# なぜユーティリティファーストが良いとされるのか

「HTML を見ただけで何をしているか分かる」だけが理由ではない。実は複数の理由が積み重なって、現代では Tailwind のようなユーティリティファーストが支持されている。

## 1. HTML を見れば全部分かる

```html
<!-- BEM の場合：これだけ見ても何もわからない -->
<button class="search-form__submit-button">送信</button>

<!-- Tailwind の場合：見れば全部わかる -->
<button class="bg-sky-500 text-white px-4 py-2 rounded">送信</button>
```

BEM だと毎回 CSS ファイルを開いて「`.search-form__submit-button` って何のスタイル当たってるんだっけ？」を確認する必要がある。Tailwind は **HTML がスタイルの宣言場所そのもの**。

## 2. 削除が安全になる

セマンティック CSS の地獄が「**削除できない CSS**」問題。

```css
/* 5年前に誰かが書いたやつ。まだ使われてる？ */
.legacy-header__menu-item--active { ... }
```

このクラスを消していいか分からない。HTML を全文検索しないと判断できない。だからどんどん CSS が肥大化する。

Tailwind なら HTML を削除すれば CSS も自動で消える（パージされる）。**死んだコードが溜まらない**。

## 3. 命名コストがゼロ

セマンティック命名は「名前を考える」のが想像以上に重い作業。

```html
<!-- これは何て名前にすればいい？ -->
<div class="???">
  <div class="???">
    <span class="???">タイトル</span>
  </div>
</div>
```

`wrapper`、`container`、`inner`、`box`、`content`、`item`...と命名で消耗する。Tailwind は **そもそも命名しない**。

## 4. 変更の影響範囲が明確

セマンティック CSS の怖いところ。

```css
/* これを書き換えると...どこが壊れる？ */
.card__title {
  font-size: 18px;
}
```

`.card__title` を使っている画面全部に影響する。一見便利だが、**「他の画面の見た目が変わってないか」を確認しないと安心して変更できない**。

Tailwind なら HTML の該当箇所だけ書き換える。**そのファイル以外には絶対に影響しない**。

## 5. デザインシステムを config で強制できる

```js
// tailwind.config.js
colors: {
  primary: colors.sky,
}
```

設定で許可した色しか書けない。BEM だと「あれ、`#5da7f0` と `#5fa9f1` どっちが正しいんだっけ」みたいなブレが必ず起きる。**人の規律ではなくツールで一貫性を担保できる**。

## 6. コンポーネント時代に最適

ここが Tailwind が登場した「時代背景」の核心。

### 昔の CSS 観

```
HTML（構造） と CSS（見た目） は分けるべき（関心の分離）
```

これが BEM の前提。

### 今の CSS 観

```
コンポーネント（HTML + CSS + JS の塊） が分離の単位
```

React や Vue のコンポーネント時代は、**1 つのボタン部品の中に HTML・CSS・ロジックが全部入ってる**のが自然。

```jsx
function PrimaryButton({ children }) {
  return <button className="bg-primary px-4 py-2 rounded">{children}</button>;
}
```

このとき CSS だけ別ファイルに切り出す意味が薄い。「ボタンを使い回したいなら関数（コンポーネント）を呼び出せばいい」「CSS の再利用は関数の再利用で十分」となる。

## 7. パフォーマンス面でも有利

- 使ったクラスしか CSS に含まれない（パージ）
- 結果として CSS ファイルサイズが小さい
- ブラウザのキャッシュにも乗りやすい

## 思想転換：「関心の分離」の意味が変わった

ユーティリティファーストが受け入れられた一番大きな背景がこれ。

| 時代          | 関心の分離の単位        | 適した CSS 設計         |
| ------------- | ----------------------- | ----------------------- |
| 〜2015 頃     | 技術ごと（HTML/CSS/JS） | セマンティック BEM      |
| 2015 頃〜現在 | コンポーネントごと      | ユーティリティ Tailwind |

「HTML と CSS が混ざるのは汚い」という昔の感覚を、「コンポーネントの中で HTML と CSS が同じ場所にあるのは自然」に上書きした、という構造。

## まとめ

| 観点                     | 内容                                             |
| ------------------------ | ------------------------------------------------ |
| HTML を見れば全てわかる  | CSS ファイルを開かなくて済む                     |
| 削除が安全               | HTML を消せば CSS も消える。死コードが溜まらない |
| 命名コストゼロ           | 名前を考える時間が無くなる                       |
| 影響範囲が局所的         | 他画面を壊す心配がない                           |
| 設定で一貫性を強制       | デザインシステムをツールで担保できる             |
| コンポーネント時代に合う | React/Vue の関心の分離単位と一致                 |
| パフォーマンスも良い     | パージで CSS が肥大化しない                      |

これらが積み重なって、現代では Tailwind が支持されている。
「HTML だけ見て分かるから」は最大のメリットではあるが、**コンポーネント時代の関心の分離単位の変化** という思想的な背景があるからこそ、ここまで広まった。
