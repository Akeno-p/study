# 技術選定の考え方

## Tailwind はおしゃれだから使うわけではない

Tailwind を使っているサイトがおしゃれに見えるのは、**デザインに投資しているチームがたまたま Tailwind も使っている**だけ。

- Tailwind 自体はデザインを何も持っていない。ユーティリティクラスだけ
- Bootstrap は完成デザイン（ボタン・カード・モーダル等）が付いてくる
- Tailwind を導入しただけでは見た目は変わらない。全部自分でデザインする必要がある

```
おしゃれなサイトが Tailwind を使っている ≠ Tailwind を使えばおしゃれになる
```

因果関係が逆。

## Tailwind が最も活きる条件：コンポーネント化された環境

Tailwind の特性として「同じクラスの羅列を何度も書くことになる」という点がある。
この特性を解消するのが React / Vue 等のコンポーネントの仕組み。

```jsx
// 1回定義すれば使い回せる（React の例）
function Button({ children }) {
  return (
    <button className="bg-primary-500 hover:bg-primary-600 text-white px-4 py-2 rounded">
      {children}
    </button>
  )
}

// あとは呼ぶだけ
<Button>送信</Button>
<Button>削除</Button>
```

コンポーネント化の仕組みがない環境でも Tailwind は使えるが、**Tailwind の強みが最大限に発揮されるのはコンポーネントがある環境**。

## 環境と CSS 設計の相性

どのツールが「正解」というわけではなく、**環境との相性**で選ぶのが大事。

| 環境                                   | 相性の良い CSS 設計                               | 理由                                     |
| -------------------------------------- | ------------------------------------------------- | ---------------------------------------- |
| React / Vue / Svelte 等                | Tailwind が活きやすい                             | コンポーネントで再利用できるから         |
| サーバーサイドテンプレート + 素の HTML | Bootstrap / セマンティック CSS (BEM) が活きやすい | CSS クラスで再利用する仕組みが必要だから |

例えば Django / Rails / PHP 等でテンプレートから HTML を返す構成なら、Bootstrap や BEM のようなセマンティックな設計の方が恩恵を受けやすい。

**大事なのは「何が流行っているか」ではなく「自分の環境に何が合っているか」**。

## コンポーネント化されていない環境での選択肢

フロントが HTML + CSS + jQuery（バニラ JS）のような構成の場合、以下のような選択肢がある。

### 選択肢 1：Bootstrap を使う

```html
<!-- これだけで再利用可能なボタンになる -->
<button class="btn btn-primary">送信</button>
```

- 完成デザインが付いてくる
- クラス名だけで再利用できる（コンポーネント化不要）
- 見た目を変えたいなら CSS 変数やテーマの上書きで対応

### 選択肢 2：BEM で自前のセマンティック CSS を書く

```html
<button class="button button--primary">送信</button>
```

```css
.button {
  padding: 8px 16px;
  border-radius: 6px;
}
.button--primary {
  background: #0ea5e9;
  color: white;
}
```

- 完全に自由なデザインができる
- クラス名で再利用できる
- 命名規則が統一されていればチームでも管理しやすい
  ーネントとの組み合わせが使えないぶん、運用には工夫が必要。

### 共通するポイント

コンポーネント化されていない環境では、**CSS のクラス名自体が「再利用の仕組み」を担う**。
そのため、セマンティックな CSS の方が恩恵を受けやすい傾向がある。

## Tailwind 導入を検討するなら

CSS フレームワークだけを差し替えるのではなく、**フロントエンド全体の設計と合わせて検討する**と、Tailwind の強みを最大限に活かせる。

```
パターンA：CSS フレームワークだけ差し替え
  → Tailwind の強みを活かしきれない可能性がある

パターンB：フロント全体をコンポーネント化 + Tailwind
  → Tailwind の強みが最大限に発揮される
```

**「分かった上であえてこうした」と「分からずにこうなった」は、成果物が同じでも評価が全く違う。**

## まとめ

- Tailwind = おしゃれツールではない。コンポーネント時代の CSS 設計ツール
- どのツールにも得意な環境がある。技術選定は環境との相性で決める
- コンポーネント化された環境なら Tailwind、そうでなければ Bootstrap や BEM も有力な選択肢
- その判断ができること自体がエンジニアとしての強みになる
