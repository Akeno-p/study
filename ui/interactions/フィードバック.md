# フィードバック

フィードバックとは、ユーザーの操作に対して、システムが反応を返すこと。

現実世界では、何かをすると自然にフィードバックが返ってくる。

例えば、ペットボトルの水を飲むとする。

```md
ペットボトルを持つ:
手にペットボトルの感触がある

キャップを回す:
キャップの感触や、力を入れている感覚がある

口をつける:
唇にペットボトルの感触がある

水を飲む:
水が口に入った感覚がある
```

このように、現実世界では何かをすると、手触り、重さ、音、抵抗、変化などで反応が返ってくる。

一方で、画面上のUIは、基本的には平面の見た目だけでできている。
そのため、反応を意図的に作らないと、ユーザーは「操作できているのか」「今どういう状態なのか」がわかりにくい。

UIでは、現実世界で自然に返ってくるような反応を、見た目、動き、メッセージ、状態変化で再現する必要がある。

## 状態を伝える

フィードバックは、単に動きを付けることではない。
ユーザーに、今の状態を伝えるために使う。

例えば、次のような状態がある。

```md
押せる
押せない
入力できている
入力内容に問題がある
処理している
成功した
失敗した
```

状態が見た目で伝わると、ユーザーは次に何をすればよいか判断しやすくなる。

## 会員登録ページの例

例えば、会員登録ページでは、次のようにフィードバックを返す。

```md
入力前:
登録ボタンがグレーアウトしていて、まだ押せないとわかる

入力中:
入力内容に問題があれば、エラーメッセージが出る

修正後:
エラーが消えて、登録ボタンに色がつき、押せる状態になる

ホバー時:
ボタンの見た目が変わり、操作できることがわかる

クリック後:
送信中の表示になる

完了後:
成功通知が出る、またはページが遷移する
```

このように、操作する前、操作している最中、操作した後で、それぞれ必要な反応を返す。

ユーザーはその反応を見ることで、今できること、問題がある場所、操作が受け付けられたこと、完了したことを理解できる。

## フィードバックは速く返す

ユーザーが操作したら、できるだけすぐに反応を返す。

ボタンを押したのに何も変わらないと、ユーザーは次のように感じやすい。

```md
押せていないのか
もう一回押した方がいいのか
処理が止まったのか
```

処理に時間がかかる場合でも、まずは「操作を受け付けた」ことを伝える。

例えば、次のような表現がある。

- ボタンを「送信中」に変える
- ローディングを出す
- ボタンを一時的に押せなくする

完了結果をすぐに返せない場合でも、操作を受け付けたことはすぐに返す。

## 次に何をすればよいかを伝える

エラーを出すときは、何が問題なのかだけでなく、どう直せばよいかも伝える。

```md
よくない例:
エラーが発生しました

よい例:
パスワードは8文字以上で入力してください
```

ただ「ダメ」と伝えるだけだと、ユーザーは次に何をすればよいかわからない。

どう直せば先に進めるのかまで伝えると、迷いにくくなる。

## 操作の重要度に合わせて強さを変える

すべての操作に強いフィードバックを出すと、画面がうるさくなる。

フィードバックの強さは、操作の重要度に合わせる。

```md
小さい操作:
ホバー、色の変化、チェックマーク

重要な操作:
成功通知、完了メッセージ、画面遷移

危険な操作:
警告表示、確認ダイアログ、取り消し導線
```

小さな操作には小さな反応でよい。
重要な操作や失敗すると困る操作には、はっきりした反応を返す。

## 状態ごとの見た目を混ぜない

UIには、いろいろな状態がある。

```md
ホバー:
今カーソルが乗っている

選択中:
今その項目が選ばれている

エラー:
今その入力内容に問題がある

無効:
今その操作はできない

処理中:
今システムが処理している
```

これらはそれぞれ意味が違う。
そのため、同じ見た目にしすぎると混乱しやすい。

例えば、ホバー状態とエラー状態が同じ赤色だと、ユーザーは「触っているだけなのか」「問題があるのか」を判断しにくい。

状態ごとに意味が伝わるように、見た目を分ける。
