# アトミックデザインについて

最も小さい単位からコンポーネントを設定して、デザインに一貫性を持たせつつ、パーツ(コード)を再利用を最大化する方法

アトミックデザインは、原子、分子、有機体、テンプレート、ページ　の5つから構成される

## 🔬 Atoms（原子）

最も小さいコンポーネント。
色、フォント、アニメーションなどの抽象的な要素（state）を含むことができる。

▼ 代表的なAtoms

- ボタン（Button）
- テキスト（Text）
- アイコン（Icon）
- 入力フィールド（テキスト入力、チェックボックス、ラジオボタンなど）
- ローディングスピナー
- トグルスイッチ
- ホバー時の色変化、フォーカス時のリング表示などのアニメーション

### 🎨 Atomsの段階で色のルールを決めておく

Atomsを定義するときに、パーツごとに使う色も決めておく。

▼ 例：ボタンの色ルール（Tailwindの場合）

- 成功・確定系 → `sky-500`
- 削除・危険系 → `red-500`
- 補助・キャンセル系 → `gray-400`

色だけでなく、テキストもフォント・サイズ・色を役割ごとにセットで決めておく。

▼ 例：テキストのルール

- 本文 → フォント: Noto Sans JP / サイズ: 14px / 色: `gray-700`
- ページ見出し → フォント: Noto Sans JP Bold / サイズ: 24px / 色: `gray-900`
- モーダルやカードの見出し → サイズ: 18px / 色: `gray-800`
- 補助テキスト → サイズ: 12px / 色: `gray-400`
- リンクテキスト → サイズ: 14px / 色: `sky-500`

こうしておくと、上の階層（Molecules〜Pages）を組み立てるときに見た目の判断をいちいちしなくて済む。
Atomsで決めたルールをそのまま使うだけで、サービス全体に一貫性が生まれる。

## 💧 Molecules（分子）

それぞれ独立した役割を持つAtomsを組み合わせて、一つの機能を作ったもの。

▼ 代表的なMolecules

- 検索フォーム — 入力フィールド（Atom）＋ 検索ボタン（Atom）
- ナビゲーション（Navigation）
- カード（Card）

例えば検索フォームなら、入力フィールドだけでは検索できないし、ボタンだけでも検索できない。
組み合わせて初めて「検索する」という機能になる。これがMolecule。

### 🤔 AtomsとMoleculesの境界は厳密ではない

例えば「虫眼鏡アイコン + テキスト + ホバーアニメーション」を持つ検索ボタン。
これは複数の要素が入っているから、Moleculeと言えなくもない。

でも「検索ボタン」として一つの部品で管理したいなら、Atomsとして扱っても問題ない。

どちらが正解かは場合による。というかプロジェクトによる。

大事なのは、**プロジェクトやチーム内で「うちではこう分類する」を統一しておくこと**。
アトミックデザインの目的は厳密な分類ではなく、パーツの粒度と再利用のルールをブレさせないことにある。

## 🪣 Organisms（有機体）

MoleculesやAtomsを組み合わせて、画面上の一つのエリア・セクションを形成したもの。
「画面のこの部分」と指差せるくらいのまとまり。

▼ 代表的なOrganisms

- ヘッダー（ロゴ + ナビゲーション + 検索フォーム）
- フッター
- 商品カード一覧（カードを並べたグリッド）
- 編集モーダル

### 🔧 Organismsは共通化して中身を差し替える

例えば、編集モーダルは用途によって中身が違う。

- 社員情報の編集 → 社員番号、氏名
- 得意先情報の編集 → 会社名、住所、電話番号

でもモーダルの見た目や振る舞い（開閉、背景暗転、ボタン配置）は共通。
なので、用途ごとに別のOrganismを作るのではなく、共通部分を一つのOrganismにして中身だけ差し替える。

```
EditModal（Organism）
├── モーダル枠
├── 見出し
├── フォーム項目（← ここを差し替える）
├── キャンセルボタン
└── 登録ボタン
```

これがアトミックデザインの「再利用を最大化する」という考え方。

### 📐 サイズのバリエーションを用意しておく

中身の項目数によってモーダルの大きさや並べ方は変わる。
あらかじめパターンを決めておくと、新しい画面を作るときに迷わない。

- **Small** — 項目1〜2個（社員番号と氏名だけ、など）
- **Medium** — 項目3〜6個（得意先情報など）
- **Large** — 項目7個以上（詳細な登録フォームなど）

モーダルの幅、項目の並べ方（1列 or 2列）、スクロールの有無などをバリエーションごとに決めておく。

ただし、あまり細かく分けすぎると管理が大変になるので、2〜3パターンくらいに収めておくのが現実的。

## 🏞️ Templates（テンプレート）& 📄 Pages（ページ）

Organismsを画面上に配置して、一つの画面を作り上げる階層。
概念としてこの2つは分かれていて、決定的な違いは**データを持っているかどうか**にある。

### 🦴 Template（骨組み）

レイアウトの枠組み。「ここにヘッダー、ここにメインコンテンツ」という配置のみを行う。
API通信などのデータ取得は行わず、ダミーデータ（引数）を受け取って表示するだけ。
ローディング中やエラー時の見た目もここで定義する。

### 📄 Page（完成形）

Templateに実際のデータ（APIやDBから取得した本物の情報）を流し込んだもの。
URL（ルーティング）と直接結びつき、状態管理やビジネスロジックを担当する。

厳密に分ける最大のメリットは、API通信を持たないTemplateを切り出すことで、Storybookなどで「画面全体のデザイン確認」が劇的に楽になること。

### 💡 現場のリアル：実務では「4階層モデル」になりがち

アトミックデザインは5階層が基本だが、実際の開発現場ではTemplateを省略して**4階層（Atoms → Molecules → Organisms → Pages）**で運用するケースが非常に多い。

▼ なぜTemplateは省略されがちなのか？

- **PageがTemplateの役割を兼ねられる** — Pageの中でOrganismsを並べてレイアウトを組みつつ、データも取得すれば1ファイルで完結する。「わざわざガワ（Template）と中身（Page）でファイルを分けるのは面倒」というのが現場のホンネ
- **再利用する機会が意外と少ない** — 「将来使い回すかも」とTemplate化しても、結局そのページ専用のレイアウトで終わることが多い
- **AI生成やスピード重視の開発と相性が良い** — AIに「これらのOrganismsを使ってこの画面を作って」と指示を出す際、中間にTemplateを挟むとファイル数が増えて取り回しが悪くなる

### まとめ

大規模開発で画面のカタログ化（Storybook等）をガッツリ運用する場合はTemplateを分けるメリットが大きい。
だが「そこまで厳密にやらない」「開発スピードを優先する」場合は、Templateは作らずOrganismsから直接Pageを作るという割り切りが、今の現場のデファクトスタンダードになりつつある。
