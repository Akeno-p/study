# SQLite

ファイルベースのデータベース。
DBサーバーを別途立てる必要がなく、アプリケーションサーバー上に`.sqlite3`ファイルとして配置するだけで動作する。


## 特徴

- DBサーバー不要。ファイル1つで完結する
- 軽量でセットアップが簡単
- 読み込みは同時にできるが、書き込みは1件ずつしかできない(複数同時に書き込まれるアプリには向かない)

## 向いているケース

- プロトタイプ・開発環境
- 並列でのトランザクション処理が出来なくても問題なく、その要件が動かないアプリ

## 向いていないケース

- 同時書き込みが多い（ファイル全体をロックするため、順番待ちが発生する）
- アプリサーバーを複数台に分散する構成（各サーバーに別々のファイルができてデータがバラバラになる）
- 動作中に書きこんだファイルが保持されないホスティング（Heroku, Cloud Runなど）

## 容量

- SQLite自体の仕様上の最大サイズは約281TB（実質無制限）
- 実際の上限はサーバーのディスク容量に依存する

## インストールが不要な理由

PostgreSQL や MySQL は「常に裏で動いていて、接続を受け付ける別のプログラム」で、
PC やサーバー本体にインストールして起動しておく必要がある。

SQLite はそういうプログラムではなく、`db.sqlite3` というファイルを直接読み書きする仕組みのため、ファイルが1つあるだけで済む。

## 同時アクセスの実際

| | 読み込み同士 | 読み込みと書き込み | 書き込み同士 |
|---|---|---|---|
| 以前（初期設定） | 同時にできる | 待たされる | 1つずつ |
| WAL モード | 同時にできる | 互いを待たない | 1つずつ |

- 読み込みは同時に何件でもできる。これは以前からそう
- WAL モードで、読み込みと書き込みが互いを待たなくなった
- 書き込み同士は今でも1つずつ。ここは変わっていない

## WALモード
sqliteは通常 読み込みと書き込みを同時に行うことができなかったが、WALモードにすることで読み込みと書き込みが同時にできるようになった。

WALモードは SQL で以下の命令を実行することで有効にできる。
```
PRAGMA journal_mode=WAL;
```

## 「本番で SQLite」が増えている理由

以前は「本番はダメ」と言われていたが、最近は本番でもsqliteを使用されることが増えてきた。

1. **SQLite 自体の改善**： WAL モードで実用上の同時アクセス性能が上がった
2. **周辺ツールの登場**： Litestream などで、ファイルを外部ストレージへ継続的にバックアップ・復元できるようになった
3. **ハードウェアの進化と考え方の変化**： サーバー1台が十分速く、ほとんどの Web サービスは1台で捌ける。「最初から複数台を前提にしない」考えが広まり、1台で完結するなら SQLite の制約は問題にならない
4. **運用が楽**： 別プログラムのインストール・起動・ユーザー管理が一切不要。ファイル1つをバックアップすれば済む

### 今でも向かないケース

- 書き込みが多く、同時に大量の書き込みが発生する（書き込みは1つずつのため）
- アプリのサーバーを複数台にして DB を共有したい
- PostgreSQL 固有の機能（高度なデータ型、拡張機能など）が必要

### そのほかの細かい違い

- **型が緩い**：数値の列に文字列を入れてもエラーにならずそのまま保存される。PostgreSQL は拒否する。
- **ユーザー・権限の管理が無い**：PostgreSQL は「このユーザーはこのテーブルだけ読める」といった制御ができるが、SQLite はファイルの読み書き権限しかない
- **機能が少ない**：使えるデータ型や `ALTER TABLE` でできることが限られる

## 本番で使用するかの判断基準

スケールせず、書き込みを並列で処理できなくて良い場合は、`sqlite`でよさそう。 (LP、HP、管理者が日記を投稿する程度のサイトなど)
ただ迷ったら後からdbを移行するのはめんどくさいので`postgresql`や`mysql`の方が良さそう。
