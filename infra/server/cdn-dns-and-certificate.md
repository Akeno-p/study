# CDNを使うときのDNSと証明書

CDNそのものの仕組み（コピーを近いサーバーから返す）は [cdn.md](../../knowledge/web-technologies/cdn.md)。ここでは、CDNを使うときにDNSと証明書がどうなるかをまとめる。

## CDNを使うかは運営者が決める

勝手にコピーが作られるわけではない。サイトの運営者がCDN会社（Cloudflare、Akamai、Amazon CloudFront など）と契約して、DNSの設定を変える。CDNは「自分のサーバーの手前に置くサービス」の1つ（[front-services.md](front-services.md)）。

|                                  | 誰が決めるか  |
| -------------------------------- | ------------- |
| CDNを使うか、どのCDN会社を使うか | 運営者        |
| どの拠点にコピーを置くか         | CDN側が自動で |

Vercel や Netlify などのホスティングサービスは最初からCDNが組み込まれているので、自分で設定しなくてもCDN経由になる。

## DNSが答えるのはCDNサーバーのIPアドレス

CDNを使うと、DNSの台帳（権威DNSサーバーが持っている「ドメイン名 → IPアドレス」の記録）ではドメイン名に対応するIPアドレスがCDNサーバーのものになる。利用者は最初からCDNサーバーにつながり、オリジンサーバー（中身の元を持っている本体のサーバー）のIPアドレスは知らない。

```
利用者      → DNS         : 「example.com は 104.16.xxx.xxx（CDN）」
利用者      → CDNサーバー : ページをもらう
CDNサーバー → オリジン    : コピーがなければ取りに行く
```

CDNサーバーは、リクエストに含まれるドメイン名から「どのサイトへのアクセスか」を特定して、そのサイトのオリジンに取りに行く。そのため、オリジンの場所をCDN側にも伝えておく必要がある。

### 設定のしかた

| 方式                      | 例         | DNSの台帳に書くもの                        | オリジンの場所の伝え方  |
| ------------------------- | ---------- | ------------------------------------------ | ----------------------- |
| DNSごと任せる             | Cloudflare | オリジンのIPアドレス（プロキシON）         | 台帳の同じ行で兼ねる    |
| 向き先だけ変える（CNAME） | CloudFront | CDN側のドメイン名（`xxxx.cloudfront.net`） | CDNの管理画面で別に登録 |

CNAMEは、台帳に「このドメインは別のドメインと同じ」と書く書き方。IPアドレスを直接書かないので、CDN側が自由にIPアドレスを変えられる。

Cloudflare の場合は次の手順。

1. Cloudflare にドメインを追加する
2. レジストラで、担当DNSサーバー（NSレコード）を Cloudflare のものに変える（[dns.md](../../knowledge/web-technologies/dns.md) の「ドメインを取る時の流れ」）。Cloudflare がこのドメインの権威DNSサーバーになる
3. DNS設定の行のプロキシ（雲のマーク）をONにする。聞かれたときにオリジンのIPアドレスを伏せて、Cloudflare のIPアドレスを答えるようになる

Cloudflare がDNSごと任せる方式にしているのは、答えるIPアドレスを自分の判断で変えられて、証明書の発行に必要な「ドメインの持ち主か」の確認（[tls.md](../../security/tls.md) の「偽物のサイトも証明書を取れるのでは？」）も自動でできるから。

## 全拠点が同じIPアドレスを名乗る

Cloudflare は世界中の拠点が同じIPアドレスを名乗っていて、ネットワークが一番近い拠点に届ける（エニーキャスト）。8.8.8.8 と同じ仕組みで、詳しくは [dns.md](../../knowledge/web-technologies/dns.md) の「8.8.8.8 は1台ではない」。

| 理由                           | 内容                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| DNSの答えが1つで済む           | 拠点ごとにIPアドレスが違うと、DNSが利用者の場所を推測して選ぶ必要がある。DNSに聞いてくるのはフルリゾルバーなので、場所を外すことがある |
| 拠点が落ちても自動で切り替わる | 落ちた拠点が名乗るのをやめるだけ。DNSの書き換えやTTL切れを待たなくていい                                          |
| 攻撃を分散できる               | DDoS攻撃（大量のアクセスでサーバーをパンクさせる攻撃）の通信が、世界中の拠点に分かれて届く                         |

Akamai や CloudFront は、問い合わせてきた場所に応じて、近い拠点のIPアドレスをその都度変えて返す。

## 証明書

### CDNサーバーに置く

ブラウザが証明書を確認する相手は、直接つながっているCDNサーバー。だからCDNサーバーに、そのドメインの証明書と秘密鍵が必要になる。Cloudflare は自分で証明書を発行して、全拠点に配置している。

つまりCDNのところで暗号化が一度解かれる。それを避けたいシステムでは使えない（[cloudflare.md](../../services/cloudflare.md) の「手前に置くサービスを使わない理由」）。

拠点ごとにIPアドレスが違っても問題ない。証明書が保証しているのは「ドメイン名と公開鍵」の組み合わせで、IPアドレスは入っていないから（[tls.md](../../security/tls.md) の「証明書とは」）。

CDNサーバーには、利用しているサイトの数だけ証明書がある。どれを出すかは、ブラウザがハンドシェイクの最初に伝えるドメイン名（SNI）で選ぶ（[certificate-and-signature.md](../../security/certificate-and-signature.md) の「接続の流れ」）。

### オリジンサーバーにも置く

通信は2区間に分かれる。

```
利用者 ⇄ CDNサーバー ⇄ オリジンサーバー
     [区間A]      [区間B]
```

オリジンに証明書がないと、区間Bは暗号化されない。ブラウザが見ているのは区間Aだけなので、鍵マークは表示されたままで、利用者は気づけない。

Cloudflare では区間Bの扱いを選べる。

| 設定              | 区間B              | オリジンの証明書                                  |
| ----------------- | ------------------ | ------------------------------------------------- |
| Flexible          | HTTP（暗号化なし） | 不要                                              |
| Full              | HTTPS              | 必要（偽物でも通してしまう）                      |
| **Full (strict)** | HTTPS              | 必要（正しい証明書か確認する）。これがおすすめ    |

オリジンに置くのは、Let's Encrypt の証明書か、Cloudflare Origin CA 証明書。Origin CA 証明書は Cloudflare だけが信頼する区間B専用の証明書で、ブラウザからは信頼されないが、有効期限を最長15年にできる。
