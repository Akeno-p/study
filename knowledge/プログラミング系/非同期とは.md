# 非同期とは

**処理を依頼したら、終わるのを待たずに次へ進むこと。**

```text
同期:   依頼する → 終わるまで待つ（その間は止まる）→ 返事 → 次へ
非同期: 依頼する → 待たずに次へ（他のことをする）→ 返事が来たら続きをやる
```

「返事を待っている間、止まらずに別のことをする」という一般的な考え方の名前で、ブラウザ側でもサーバー側でも同じ意味で使う。

## 「ページ更新なし」は非同期の定義ではない

Ajax のイメージから「非同期 = ページを更新せずに処理する仕組み」と思いがちだが、それは非同期を使った結果の一つで、定義ではない。Ajax は次の2つの性質を組み合わせたもの。

| 性質           | 何によって実現しているか                                               |
| -------------- | ---------------------------------------------------------------------- |
| ページ更新なし | JavaScriptから通信し、返ってきたデータでページの一部だけ書き換える     |
| 非同期         | JavaScriptが返事を待たずに先へ進む（待っている間も画面の操作ができる） |

2つが別物である証拠に、JavaScriptの通信機能（XMLHttpRequest）には「返事が来るまで止まって待つ」同期モードがある（今は非推奨）。同期モードで通信すると、ページは更新されないのに、返事が来るまで画面が固まる。

## 同期で止まるのは「処理」だけではなく、ページ全体

ブラウザは1つのタブについて、次の仕事をすべて同じ1つの担当が順番にこなしている（この担当を「メインスレッド」と呼ぶ）。

- JavaScriptの実行
- クリック・文字入力の受付
- 画面の描き換え

JavaScriptが同期通信で返事を待つと、この担当ごと止まる。JavaScriptだけが止まって他は動く、という分業にはなっていない。

「送信中の表示」「二重送信を防ぐためにボタンを押せなくする」「×で閉じる」のような当たり前に見える動きも、非同期があって初めて成り立つ。利用者が待ち時間に何もしないとしても、「画面が固まる」こと自体がユーザー体験(UX)を下げる。

## アプリケーションサーバー側の非同期

|                           | 誰が                 | 何を待つ間に          | 待っている間に何をするか                       |
| ------------------------- | -------------------- | --------------------- | ---------------------------------------------- |
| ブラウザ側（Ajax、fetch） | ブラウザのJavaScript | サーバーからの返事    | 画面の操作を受け付け続ける（画面が固まらない） |
| サーバー側                | ワーカー             | DBや外部APIからの返事 | 別のリクエストを処理する                       |

アプリケーションサーバーでは、ワーカーがDBの返事を待っている間は何もせず待つ（同期）が採用されることが多いが、非同期のアプリケーションサーバーも存在する。
非同期のアプリケーションサーバーではワーカーがDBの返事を待っている間に別のリクエストを受け取って処理することができるため、1つのワーカーで多数のリクエストを同時に扱える。

### なぜアプリケーションサーバーは同期が多いのか

ブラウザでは非同期が必須なのに、アプリケーションサーバーで同期が主流なのは、**担当が1人か複数か** の違いが大きい。

|                      | ブラウザ                              | アプリケーションサーバー                         |
| -------------------- | ------------------------------------- | ------------------------------------------------ |
| 担当の数             | 1人（メインスレッド）                 | 複数（ワーカー）                                 |
| 同期で待つと         | 全部止まる                            | そのワーカー1つが止まるだけ。他のワーカーは動く  |
| 同期のまま増やせるか | 増やせない | 増やせる（メモリを足してワーカーを増やせばいい） |

サーバーはもともとワーカーが複数いるので、同期の代償は「待っている間のメモリの無駄」だけ。足りなくなったらワーカーを増やすという単純な手もある。

そのうえで、同期が選ばれる理由が4つある。

1. **非同期は1件を速くするものではない**: DBが返事に0.05秒かかるなら、同期でも非同期でも利用者は0.05秒待つ。非同期が変えるのは「同時に扱える数」だけなので、リクエストの数がそこまで多くないアプリでは得られるものがない
2. **アプリのコードとライブラリが全部非同期対応でないと効果がない**: 非同期ワーカーは「1箇所でも同期で待つと全部止まる」構造。DB操作や外部API呼び出し、使っているライブラリまで全部が非同期で書かれていて初めて効く。
3. **同期の方が失敗が局所的**: 遅い処理やバグが起きても、同期なら塞がるのはそのワーカー1つだけで、管理役が制限時間で強制終了して立て直せる。非同期だと、1リクエストのミスで同じワーカーが扱っている他の人まで巻き添えになる
4. **言語の歴史**: Python・Ruby・PHP は同期前提で育った言語で、ライブラリも開発者の慣れも同期側にある。逆に Node.js はブラウザのメインスレッドから生まれた JavaScript の言語なので、最初から非同期が標準

実際には全部を非同期にするのではなく、**同期ワーカーを基本にして、必要な部分だけ非同期に切り出す** のが一般的。

- チャットや通知のような「つなぎっぱなし」の機能だけ、別の非同期サーバーで動かす
- 外部APIを呼ぶような時間のかかる処理は、リクエストの中でやらず、別のプログラム（バックグラウンド処理）に渡してすぐ返事を返す


#### 補足: なぜ「つなぎっぱなし」には非同期サーバーが必要なのか

チャットや通知で新着を知らせる方法は2つある。

| 方式             | 仕組み                                                                   | 同期サーバーで作れるか |
| ---------------- | ------------------------------------------------------------------------ | ---------------------- |
| ポーリング       | ブラウザが「新着ある？」と数秒おきに問い合わせる                         | 作れる                 |
| つなぎっぱなし   | 接続を切らずに保っておき、新着が出たらサーバーの方から送る | 作れはする     |

ポーリングは無駄なリクエストが大量に来る（利用者1000人が1秒おきに問い合わせると、ほとんどが「ない」という返事なのに1秒に1000件）うえ、問い合わせの間隔の分だけ反映が遅れる。つなぎっぱなしならどちらも起きないが、サーバーは接続している全員分の接続を保ち続ける必要がある。

同期サーバーでも、1つの接続にワーカーを1つ占領させればつなぎっぱなしは作れるが、やろうとすると
**接続数分のワーカーが必要になる。** 
接続数 = 必要なワーカーの数なので、接続数が10,000なら ワーカー10,000個（1つ50MBなら500GB）と大量のワーカーが必要になる。
しかもそのワーカーはほとんど「新着待ち」で何もしていない状態になる。

非同期サーバーなら、接続中の時間はほとんどが「新着待ち」なので、待っている間に他の接続を扱える。1つのワーカーで数千人の接続を保てる。

つまり、非同期そのものがチャットに必要なのではなく、**「つなぎっぱなし」方式を使うために非同期が必要になる** という関係。
