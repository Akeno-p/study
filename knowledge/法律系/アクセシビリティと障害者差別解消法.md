# アクセシビリティと障害者差別解消法


## 概要

アクセシビリティ対応は、単に「親切で行うもの」ではなく、サービス提供者として一定の範囲で考慮すべき事項になっている。

特に日本では、障害者差別解消法により、障害のある人に対する不当な差別的取扱いは禁止されている。また、2024年4月1日からは、民間事業者にも合理的配慮の提供が義務化された。

ただし、これは「アクセシビリティ上の不備があれば直ちに違法になる」という意味ではない。

## 関係する法律

主に関係する法律は、障害者差別解消法である。

正式名称は「障害を理由とする差別の解消の推進に関する法律」。

この法律は、行政機関等および事業者に対し、障害を理由とする不当な差別的取扱いを禁止し、障害のある人から意思表示があった場合に、合理的配慮を提供することを求めている。

2024年4月1日以前は、民間事業者における合理的配慮の提供は努力義務だった。改正法の施行により、2024年4月1日から民間事業者についても法的義務となった。

## 合理的配慮とは

合理的配慮とは、障害のある人がサービスや施設などを利用する際に、社会的障壁を取り除くための対応を求めた場合、事業者が過重な負担にならない範囲で、必要かつ合理的な対応を行うことである。

重要なのは、次の点である。

- 障害のある人が、サービス利用上の困難に直面している
- 本人、家族、介助者などから、何らかの配慮を求める意思表示がある
- 事業者側に、過重な負担なく対応できる方法がある
- それにもかかわらず、正当な理由なく対応を拒否する

このような場合には、障害者差別解消法上の問題になり得る。

一方で、あらゆる要望に無条件で応じる義務があるわけではない。対応の可否や方法は、事業の内容、規模、費用、人的体制、安全性、他の利用者への影響などを踏まえて判断される。

## アクセシビリティ対応との関係

アクセシビリティ対応は、Webサイトやアプリだけの問題ではない。実店舗、施設、交通、教育、行政手続き、医療、金融、予約、購入、問い合わせなど、サービス全般に関係する。

Webやアプリにおいては、HTMLやUI実装の不備が、障害のある利用者にとってサービス利用上の障壁になることがある。

例えば、次のような実装は避けるべきである。

```html
<div onclick="submit()">送信</div>
```

見た目上はボタンに見えても、HTML上はボタンではないため、キーボード操作やスクリーンリーダーで適切に扱えない可能性がある。

この場合は、次のように `button` 要素を使う方が適切である。

```html
<button type="submit">送信</button>
```

`button` 要素を使うことで、ブラウザや支援技術に対して「これはボタンである」という意味が伝わりやすくなる。

フォームでも同様に、入力欄には対応する `label` を設定することが望ましい。

例えば、次のように `p` 要素などで見た目上の項目名だけを置く書き方は避けた方がよい。

```html
<p>ユーザー名</p>
<input id="username" name="username" type="text" />
```

この書き方では、画面上は「ユーザー名」の入力欄に見えても、HTML上は `p` 要素と `input` 要素が明確に関連付いていない。

そのため、入力欄の意味を正しく伝えるには、次のように `label` を使う方が適切である。

```html
<label for="username">ユーザー名</label>
<input id="username" name="username" type="text" />
```

`label` の `for` 属性と `input` の `id` を対応させることで、読み上げソフトなどの支援技術が入力欄の意味を把握しやすくなる。

## 「HTMLのミスだけで即違法」ではない

アクセシビリティ上望ましくないHTMLを書いたことだけで、直ちに法令違反になるというわけではない。

問題になり得るのは、その不備によって障害のある人が購入、予約、申込み、問い合わせ、情報取得などを実質的に行えない状態になり、その状況について改善や代替手段を求められたにもかかわらず、過重な負担がないのに正当な理由なく対応しない場合である。

したがって、エンジニア個人が「`alt` 属性を書き忘れたから即違法」という話ではない。

より正確には、事業者が提供するサービスにおいて、障害のある人の利用を妨げる障壁があり、合理的配慮の要請に対して適切に検討・対応しない場合に、法的な問題になり得るという理解が妥当である。

## 実店舗での例

実店舗の場合、例えば車椅子利用者から「入口の段差があり入店しづらいので対応してほしい」と申し出があったとする。

その場合、事業者は状況に応じて、次のような対応を検討する必要がある。

- 簡易スロープを出す
- スタッフが補助する
- 段差のない別入口を案内する
- 店舗外で注文や受け渡しを行う
- 別の利用方法を提案する

一方で、建物の構造、費用、安全性、人員体制などの事情により、希望された方法をそのまま実現できない場合もある。その場合でも、単に拒否するのではなく、代替案を含めて建設的に対話することが重要である。

「面倒だから対応しない」「うちはそういう対応をしていない」「使えないなら諦めてほしい」といった対応は、正当な理由がない場合、問題になり得る。

## エンジニアが理解しておくべきこと

エンジニアにとって重要なのは、アクセシビリティ対応を単なる品質向上や善意の問題としてだけ扱わないことである。

Webサイトやアプリは、事業者が提供するサービスの入口になることが多い。その入口が使えない場合、障害のある人にとっては、購入、予約、申請、問い合わせ、情報取得といった行為そのものが妨げられる可能性がある。

そのため、セマンティック(意味が明確な)なHTMLを書く、キーボード操作に対応する、フォームに適切なラベルを付ける、画像に必要な代替テキストを設定する、エラー内容を分かりやすく伝える、といった実装は、単なる作法ではなく、サービスを利用可能にするための基礎的な対応である。

## まとめ

アクセシビリティ対応は、「親切でやるもの」にとどまらず、サービス提供者として、障害のある人が利用できるように過重な負担のない範囲で対応を検討すべきものになっている。

一方で、すべてのWebサイトやアプリ、店舗、施設を直ちに完全対応しなければ違法になる、という理解は正確ではない。

実務上は、アクセシビリティ上の障壁をできるだけ事前に減らし、利用者から配慮の申し出があった場合には、正当な理由なく拒否せず、建設的対話を通じて必要かつ合理的な対応を検討することが重要である。
