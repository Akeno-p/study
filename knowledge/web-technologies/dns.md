# DNS

## DNSとは

ドメイン名（youtube.com など）とIPアドレスを紐づける仕組み。ブラウザはドメイン名のままではサーバーに接続できないので、まずDNSでIPアドレスを調べてから接続する。

## 偽のDNSサーバーは誰でも建てられる

「youtube.com → 攻撃者のサイトのIPアドレス」と答えるDNSサーバーは、誰でも建てられてしまう。

だから「**そのドメインの正しい情報を持っているのはどのサーバーか**」を、上位から案内してもらう仕組みがある。

## 登場人物

### DNSサーバーの種類

| 名前                 | 役割                                           | 例                                                          |
| -------------------- | ---------------------------------------------- | ----------------------------------------------------------- |
| **フルリゾルバー**   | PCの代わりに問い合わせて回る係                 | プロバイダーのDNSサーバー、8.8.8.8（Google）、1.1.1.1（Cloudflare） |
| **ルートサーバー**   | DNSの一番上。「`.com` はあそこに聞いて」と案内 | 世界に13系統ある                                            |
| **TLDのサーバー**    | 「youtube.com の担当はあそこ」と案内           | `.com` なら Verisign のサーバー                             |
| **権威DNSサーバー**  | そのドメインの正式な情報（IPアドレス）を持つ   | youtube.com なら ns1.google.com など                        |

TLD（Top Level Domain）は `.com` や `.jp` の部分のこと。


### レジストリとレジストラ

| 名前           | 役割                                   | 例                                     |
| -------------- | -------------------------------------- | -------------------------------------- |
| **レジストリ** | TLDのデータベースを管理する組織        | `.com` は **Verisign**、`.jp` は **JPRS** |
| **レジストラ** | ドメインの申し込みを受け付ける販売窓口 | お名前.com、GoDaddy など               |

## ドメインを取る時の流れ

1. **レジストラ**に「youtube.com を取りたい。このドメインの担当DNSサーバーはこれです」と申し込む
2. レジストラが**レジストリ**（`.com` なら Verisign）に登録する
3. 「youtube.com の担当は ns1.google.com など」という情報（**NSレコード**）が `.com` のサーバーに載る

`.com` のサーバーが持っているのは「**担当サーバーはどこか**」だけ。youtube.com のIPアドレスそのものは持っていない。IPアドレスを持っているのは権威DNSサーバー。

## ドメイン名からIPアドレスにたどり着くまで

```
0. PC が自分の中を確認（ブラウザ・OSのキャッシュ、hostsファイル）
   → 見つかればここで終わり
1. PC             → フルリゾルバー     : 「youtube.com のIPを教えて」
2. フルリゾルバー → ルートサーバー     : 「.com のことは .com のサーバーに聞いて」
3. フルリゾルバー → .com のサーバー    : 「youtube.com の担当は ns1.google.com などだよ」
4. フルリゾルバー → 権威DNSサーバー    : 「IPアドレスはこれ」
5. フルリゾルバー → PC                 : IPアドレスを返す
```

- PCが聞くのは**フルリゾルバーに1回だけ**。2〜4はフルリゾルバーがやる
- フルリゾルバーも調べた結果をキャッシュしている。覚えていれば2〜4を飛ばしてすぐ5を返す

### hostsファイル

PCの中にある「ドメイン名とIPアドレスの対応表」（macOSなら `/etc/hosts`）。基本的に誰もいじらないので `localhost` くらいしか載っておらず、普段は参照されない。

### キャッシュの有効期限（TTL）

キャッシュをどれだけ残すかは、サイト側（権威DNSサーバー）が秒数で決めている。大手サービスほど短め（数十秒〜5分程度）にしていることが多い。障害時の切り替えや負荷分散で、IPアドレスをすぐ変えたいから。

|          | メリット                         | デメリット                       |
| -------- | -------------------------------- | -------------------------------- |
| 短くする | IPアドレスの変更がすぐ反映される | 問い合わせが増えて、少し遅くなる |
| 長くする | 問い合わせが減って速い           | 変更の反映が遅れる               |

## 案内であって証明ではない

この仕組みでわかるのは「**正しい情報を持っているのはどこか**」という道順だけ。届いた応答が本物かどうかを暗号的に証明しているわけではない。

## 問い合わせは暗号化されない

DNSの問い合わせと応答は、基本的に暗号化されずに流れる。

- 同じネットワークにいる人（無料Wi-Fiの運営者など）には、どのドメインを調べたかが見える
- 途中で応答を偽物に差し替えられる可能性もある

DoH（DNS over HTTPS）や DoT（DNS over TLS）という、DNS を暗号化する方式もある。ブラウザや OS の設定で有効にしていれば暗号化される。

## フルリゾルバー

使っているフルリゾルバーは、PCのネットワーク設定の「DNSサーバー」の欄で確認できる。何も設定しなければプロバイダーのもの。8.8.8.8 などの公開DNSに自分で変えることもできるし、会社や学校では組織が用意したものを使うこともある。

DNSサーバーの欄に家のルーター（`192.168.1.1` など）が書かれていることもあるが、ルーターは受け取った質問をプロバイダーのフルリゾルバーに転送しているだけ（フォワーダー）。

1.1.1.1 は Cloudflare のフルリゾルバー。CDNを使うときに Cloudflare に任せる権威DNSサーバー（[cdn-dns-and-certificate.md](../../infra/server/cdn-dns-and-certificate.md)）とは別の役割。

### キャッシュは利用者全員で共有

1台のフルリゾルバーを大勢で使っているので、キャッシュも全員で共有される。誰かが最近調べたドメインなら、自分が初めて開くサイトでもすぐ返ってくる。

- 利用者が少ないフルリゾルバーはキャッシュが少ないので、1回目だけ少し遅い（数十〜数百ミリ秒程度）
- 偽の情報を覚えさせられると、そのフルリゾルバーを使う全員が偽サイトに誘導される（DNSキャッシュポイズニング）
- キャッシュするのはドメイン名とIPアドレスなどの情報だけ。サイトの中身はキャッシュしない（中身をキャッシュするのは [CDN](cdn.md) など）

### 8.8.8.8 は1台ではない

8.8.8.8 の裏では、世界中にある Google のデータセンターで大量のサーバーが動いている。全部が同じ 8.8.8.8 を名乗っていて、問い合わせは一番近い拠点に届く（**エニーキャスト**）。キャッシュは拠点ごとに持っている。

ルートサーバーの「13系統」も同じ仕組みで、それぞれの裏に世界中のサーバーがある。
