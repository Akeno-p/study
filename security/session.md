# セッションについて

## セッションとは

Webアプリにおいて「この端末はログイン済みである」という状態を管理する仕組み。

HTTPは本来ステートレス（状態を持たない）なプロトコルなので、リクエストごとに「この人は誰？」がわからない。セッションはこの問題を解決するためにある。

## 仕組み

1. ユーザーが認証（ログイン）に成功する
2. サーバーが「セッション情報」を作成し、セッションIDを発行する
3. セッションIDをCookieとしてブラウザに渡す
4. 以降、ブラウザはリクエストのたびにCookieを自動で送る
5. サーバーはCookieのセッションIDを見て「ログイン済み」と判断する

つまり、セッションIDは「ログイン済みの証明書」のような役割。

## セッションIDが流出するリスク

セッションIDが第三者に知られると、その人がログイン済みの状態でアプリにアクセスできてしまう（セッションハイジャック）。

### 主な流出経路

- **通信の盗聴**: HTTP（暗号化なし）で通信していると、Cookieの中身が見られる可能性がある。HTTPS通信であれば通信内容が暗号化されるため防げる
- **XSS（クロスサイトスクリプティング）**: アプリに脆弱性があり、悪意あるJavaScriptを埋め込まれた場合、CookieのセッションIDを抜き取られる可能性がある

### 対策

| 対策           | 内容                                                  |
| -------------- | ----------------------------------------------------- |
| HTTPS通信      | 通信を暗号化し、盗聴を防ぐ                            |
| HttpOnlyフラグ | CookieにJavaScriptからアクセスできなくする（XSS対策） |
| Secureフラグ   | HTTPS通信の時だけCookieを送信する                     |

## HTTPSは実質必須

セッションIDは盗まれると致命的なので、セッションを使うならHTTPSは実質必須。HTTPでもセッションは動くが、盗聴されるとセッションIDが丸見えになり、盗まれてなりすまされる。

HTTP/HTTPS自体の違い（暗号化の有無、ステートレスとの関係）は [http-https.md](../knowledge/web-technologies/http-https.md) を参照。
