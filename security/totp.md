# TOTPの仕組み

TOTP（Time-based One-Time Password）は、認証アプリに表示される「30秒ごとに切り替わる6桁のコード」のこと。2段階認証の方式の1つ（[two-factor-auth.md](two-factor-auth.md)）。

核心は、**サーバーと手元の端末が同じ秘密鍵を持っていて、同じ計算をしているだけ**ということ。

## セットアップ

最初のQRコード読み取りは、**サーバーが生成した秘密鍵を端末に渡す操作**。

```
サーバー: 秘密鍵「ABCDEF123456」を生成 → QRコードとして表示
スマホ:   読み取って秘密鍵「ABCDEF123456」を保存
```

この一度きりの共有以降、秘密鍵そのものは二度と通信に流れない。

## コード生成

サーバーと端末の両方が、同じ入力で同じ計算をする。

```
HMAC(秘密鍵, 現在時刻を30秒単位で区切った値) → ハッシュ値 → 6桁を取り出す
```

同じ入力・同じ計算なので、両者は同じ6桁になる。30秒経つと時刻側の入力値が変わるので、コードも切り替わる。

### HMACとは

**鍵を入力に取るハッシュの仕組み**（Hash-based Message Authentication Code）。

普通のハッシュ関数は入力がデータだけで、誰が計算しても同じ結果になる。HMACは鍵とデータの両方を入力に取るため、**同じデータでも鍵が違えば結果が変わる**。

```
HMAC("鍵A", "hello") → 8a3b2f...
HMAC("鍵B", "hello") → e91c4d...
```

だから、秘密鍵を知らない人は時刻がわかっても正しい6桁を計算できない。

### なぜハッシュを一度挟むのか

もし「秘密鍵 × 時刻」のような単純な計算式で6桁を作ると、攻撃者は時刻（公開情報）・計算式（公開仕様）・観測した6桁から、**未知数である秘密鍵を数学的に逆算できてしまう**。

ハッシュ関数の**一方向性**（出力から入力を逆算できない）を挟むことで、6桁と時刻を知っていても秘密鍵にたどり着けなくなる（[hash-and-encryption.md](hash-and-encryption.md)）。

### 6桁の取り出し方（動的トランケーション）

HMACの計算結果は20バイトの長いデータ。そこから:

1. ハッシュ値の**最後の4ビット**の値で「どこから取り出すか」の開始位置を決める
2. その位置から4バイトを取り出して整数に変換する
3. 100万で割った余りを取る → 6桁（000000〜999999）

「常に先頭6文字」のような固定位置にしないのは、特定の位置に偏りがあった場合に推測のヒントになりうるから。取り出す位置自体をハッシュ値から決めることで、予測をさらに困難にしている。

この手順はすべて公開仕様。それでも安全なのは、安全性が秘密鍵の秘密にのみ依存しているから（ケルクホフスの原則 → [hash-and-encryption.md](hash-and-encryption.md)）。

## 認証の流れ

```
ユーザー: 表示されている「482937」を入力（一方的に提出する）
サーバー: 自分でも同じ計算をする → 「482937」→ 一致するのでOK
```

サーバーはユーザーの提出値を自分の計算結果と照合するだけで、**自分の計算結果（正解）は絶対に見せない**。サーバー側から答えを見せる設計だと、正解そのものがヒントとして漏れてしまう。

## なぜ安全なのか

- 秘密鍵を持っていない人は、正しい6桁を計算できない
- 6桁を盗み見られても、30秒後には無効になる
- 6桁から秘密鍵は逆算できない（一方向性）
- 総当たりしようにも、30秒の間に100万通りを試す必要がある

もし秘密鍵そのものを送って認証する方式だったら、一度でも傍受された時点で永続的になりすまされる（秘密鍵は変わらないので）。TOTPは「**秘密鍵を知っていることを、秘密鍵自体を通信に流さずに証明する**」仕組み。

「秘密鍵を持っている端末が手元にある」こと自体が認証になるので、パスワード（知識）と組み合わせて二要素認証が成立する。

## サーバー側での秘密鍵の保存

サーバーは検証のたびに**元の秘密鍵の値**を使ってOTPを計算する必要があるため、ハッシュ化では保存できない。かといって平文でDBに置くと、漏洩した際に攻撃者が同じ計算でOTPを生成でき、2段階認証が無意味になる。

→ アクセストークンと同じ理屈で、**暗号化してDBに保存する**（[token-storage.md](token-storage.md)）。
