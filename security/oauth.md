# OAuth

## OAuthとは

**あるアプリに、自分のデータへの、どこまでの操作を許すかを扱う仕組み。**

"Auth"は**Authentication（認証）ではなくAuthorization（認可）**。

| 用語                      | 意味                           |
| ------------------------- | ------------------------------ |
| Authentication（認証）    | 「あなたは誰か」を確かめる     |
| Authorization（**認可**） | 「あなたに何を許すか」を決める |

**OAuthは「誰であるか」を確かめる仕組みではない。** この区別が後々効いてくる（→ OpenID Connect）。

## これは業界標準の仕様

特定のサービス独自の仕組みではなく、**RFC 6749** として標準化されたWeb全体の共通規格。ほぼすべての主要サービスがこれを採用している。

| サービス                              | 用途                         |
| ------------------------------------- | ---------------------------- |
| Google                                | Gmail / Drive / Calendar API |
| GitHub                                | リポジトリ操作、CI/CD        |
| Slack                                 | Bot、ワークスペース連携      |
| X (Twitter)                           | 投稿、DM                     |
| Stripe / Notion / Discord / LINE など | ほぼ全部                     |
| Auth0 / Firebase Auth / AWS Cognito   | 認証基盤サービス             |

**「Googleでログイン」「GitHubでログイン」ボタンの裏側もこれ。** 「このアプリがあなたのプロフィールにアクセスすることを許可しますか？」という画面が、後述する**認可画面**そのもの。

### ただしプロバイダごとの差異はある

**仕組み・登場人物・フローは共通**だが、細部は各社で違う。

- エンドポイントのURL
- scope（権限）の名前
- 対応しているフローの種類
- トークンの有効期限

**「形」は同じなので迷わないが、具体的な値は毎回そのサービスのドキュメントを読む**ことになる。

## 解決したかった問題

### パスワードアンチパターン

OAuth以前は、外部サービスを使うときにそのサービスへ**対象サービスのIDとパスワードを直接渡していた**。サービス側はそれを使って本人になりすましてログインし、操作していた。

| 問題                     | 内容                                                            |
| ------------------------ | --------------------------------------------------------------- |
| パスワードを預けてしまう | サービス側がパスワードを保存する。漏洩したら終わり              |
| 権限が全か無か           | 投稿だけ許可したくても、DM閲覧もアカウント削除も可能になる      |
| 取り消せない             | やめたければパスワードを変えるしかない → 他のサービスも全部死ぬ |

「信頼するなら全権委任、しないなら使えない」という状態だった。

### 解決の発想

**本物の鍵（パスワード）を渡さず、限定された権限の合鍵を発行する。**

高級車をホテルに預けるときのバレーキーと同じ。エンジンはかけられるがトランクは開かず、走行距離にも制限があり、後から無効化できる。

この合鍵にあたるのが**アクセストークン**。

## 登場人物

| 役       | 正式名称                         | 内容                               |
| -------- | -------------------------------- | ---------------------------------- |
| 持ち主   | Resource Owner（リソース所有者） | データの持ち主であるユーザー       |
| 借りる側 | Client（クライアント）           | データを使いたいアプリ             |
| 管理者   | Authorization / Resource Server  | データを持ち、許可を出すサービス側 |

Resource（リソース）= 守られている資産。投稿、メール、リポジトリ、プロフィールなど。その**所有者（Owner）がユーザー本人**。

| 例                             | Resource Owner | Client           | Server |
| ------------------------------ | -------------- | ---------------- | ------ |
| 予約投稿サービスがXに投稿する  | Xのユーザー    | 予約投稿サービス | X      |
| CIツールがGitHubをclone        | GitHubユーザー | CIツール         | GitHub |
| アプリがGoogleカレンダーを読む | Googleユーザー | そのアプリ       | Google |

## 鍵が2組ある理由

サーバーはリクエストを受け取ったとき、**2つの独立した問い**に答える必要がある。

1. **どのアプリ**から来たか
2. **誰のデータ**を触ろうとしているか

別々の問いなので、鍵も別々になる。

| 鍵                                | 答える問い                     | 正体                 |
| --------------------------------- | ------------------------------ | -------------------- |
| **Client ID** / **Client Secret** | どのアプリか                   | **アプリの名札**     |
| **Access Token**                  | 誰のデータを、許可を得て触るか | **ユーザーの委任状** |

> **呼び名の違い**: OAuth 1.0aでは Client ID / Secret を **Consumer Key / Consumer Secret** と呼ぶ。Consumer（消費者）= APIを消費する側 = アプリ自身、という意味。
> さらにサービスによっては管理画面上の表記が "API Key / API Secret" になっていることもある（Xがそう）。**全部同じものを指している。**

### 委任状はアクセストークンの方

Client IDは「このアプリはサービスに登録済みの◯◯というアプリです」と名乗るだけのもので、**誰かから何かを委任された証拠ではない**。

対してアクセストークンには「**このユーザーが、このアプリに、自分のデータを触ることを許可した**」という関係が刻まれている。だからこそ取得にユーザーの許可操作が要る（名札をもらうのにボタンは要らない）。

Xのアクセストークンが `<user_id>-xxxxxxxx` という形式で頭にユーザーIDが付いているのは、その一例。「誰の委任状か」がトークン自体に埋まっている。

### 権限を取り消せる理由

サービス側はこの組み合わせ単位で権限を管理する。「このアプリの許可を取り消す」と設定画面で操作すれば、**そのアプリのアクセストークンだけが無効になる**。パスワードは変えなくていいし、他のアプリは無事。これがパスワードアンチパターンからの解放。

どのサービスにも「連携しているアプリ一覧」のような画面があり、そこで個別に取り消せるのはこの仕組みによる。

## アクセストークンの取得（認可フロー）

3者が関わるので **3-legged OAuth** と呼ばれる。

```
1. アプリ「これから認可を始めたい」（Client ID で名乗る）

2. アプリがユーザーをサービスの認可画面へリダイレクト
     → 「このアプリに◯◯を許可しますか？」の画面が出る

3. ユーザーが「許可する」を押す
     → サービスが「認可された」という証（code）を持たせて、
        ユーザーをアプリの callback URL へ送り返す

4. アプリ「この証を持ってきました。アクセストークンをください」
     （ここで Client Secret を使ってアプリ自身を証明する）
     → サービスがアクセストークンを発行

5. 以降、アプリはアクセストークンを使って API を叩ける
```

**callback URL（リダイレクトURI）が使われるのはステップ3。** 認可が終わったユーザーを送り返す先として、事前にサービス側へ登録しておく。

> 登録した文字列と、リクエストで送る `redirect_uri` は**完全一致**で照合される。末尾のスラッシュ1文字違ってもエラーになる。

## OAuth 2.0（現行の標準）

トークンをリクエストヘッダにそのまま載せる。

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6...
```

**Bearer = 持参人払い。** 小切手と同じで「持っている者が本人」という割り切り。

そのため**トークンが漏れたら即アウト**。これを以下でカバーする設計になっている。

- **HTTPS必須**（通信路で盗まれない）
- **短い有効期限**（漏れても被害が続かない。数十分〜数時間が一般的）

### Client Secret はどこで使うのか

**APIを叩くときには使わない。** 送るのはBearerトークンだけ。出番は**トークン交換（フローのステップ4）の1回だけ**。

```
     ブラウザ                アプリ              サービス
        |                     |                      |
        |  code=abc123        |                      |   ← ブラウザを経由するのはここまで
        |-------------------->|                      |
        |                     |  code + client_id    |
        |                     |     + client_secret  |
        |                     |--------------------->|   ← サーバー間の直接通信
        |                     |<---------------------|      （ブラウザを一切通らない）
        |                     |    access_token      |
        |   （何も見えない）  |  → DBに保存          |
```

なぜここで証明が必要か。**`code`はリダイレクトでブラウザに載って返ってくるので、盗まれる可能性がある**（悪意ある拡張機能、履歴、ログなど）。

もしClient Secretが無ければ、`code`を盗んだ第三者が**公開情報であるClient ID**と組み合わせてトークン交換リクエストを送り、アクセストークンを手に入れられてしまう。

> **Client Secretは「トークンを受け取る資格があるのは本物のアプリのサーバーだけ」を担保している。**

### なぜClient IDは「公開情報」なのか

**構造上どうやっても秘密にできないから。**

認可フローのステップ2で、アプリはユーザーをこのURLに飛ばす。

```
https://<サービス>/oauth2/authorize
    ?client_id=XXXXXXXX          ← ブラウザのアドレスバーに表示される
    &redirect_uri=http://localhost:8000/callback/
    &scope=...
    &response_type=code
```

Client IDは**ユーザーのブラウザに載る**。履歴に残るし、拡張機能からも開発者ツールからも読める。

**HTTPSで暗号化されていても関係ない。** 暗号化が守るのは「通信路の途中」であって、**終点にいるユーザーのブラウザ**は守らない（そもそもユーザーに見せるために送っている）。

|                        | Client ID                     | Access Token                     |
| ---------------------- | ----------------------------- | -------------------------------- |
| ブラウザに晒されるか   | **晒される**（認可URLに載る） | **晒されない**（サーバー間のみ） |
| 秘密でいられるか       | **無理**                      | **できる**                       |
| それ自体が証明になるか | **ならない**                  | **なる**                         |
| 別途Secretが要るか     | **要る**                      | **不要**                         |

ユーザー名とパスワードの関係と同じ。**Client ID = ユーザー名（公開してよい）、Client Secret = パスワード（絶対に見せない）。** ユーザー名を知っているだけでログインできたら困るのと同じ理屈。

> **前提**: この説明はサーバーサイドアプリ（Confidential Client）を想定している。SPAやモバイルアプリは「秘密を安全に保管できる場所がない」（解析すればClient Secretが抜ける）ため、Client Secretを使わない別の仕組み（**PKCE**）を用いる。**未学習。**

### 有効期限と scope

| 概念              | 内容                                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| **有効期限**      | アクセストークンは短命（数十分〜数時間）                                                       |
| **Refresh Token** | 期限切れ時に新しいアクセストークンを再発行するためのトークン。ユーザーに再ログインさせずに済む |
| **scope**         | 許可する権限の範囲。認可画面に「このアプリは◯◯にアクセスします」と列挙されるのはこれ           |

scopeはサービスごとに名前が違う。

| サービス | 例                                                    |
| -------- | ----------------------------------------------------- |
| X        | `tweet.read` / `tweet.write` / `dm.read` / `dm.write` |
| GitHub   | `repo` / `user` / `gist`                              |
| Google   | `https://www.googleapis.com/auth/drive.readonly`      |

**必要最小限のscopeだけ要求するのが原則**（最小権限の原則）。ユーザーは認可画面でそれを見て許可を判断する。

Refresh Tokenを受け取るには、認可リクエスト時に明示的な要求が必要なことが多い（Xなら`offline.access`スコープ、Googleなら`access_type=offline`）。

### トークンの置き場所

**アクセストークンはユーザーごとに異なる**ので、置き場所は`.env`（アプリの設定）ではなく**DB（ユーザーのデータ）**になる。

| 値                           | 置き場所               |
| ---------------------------- | ---------------------- |
| Client ID / Client Secret    | `.env`（アプリ固有）   |
| Access Token / Refresh Token | **DB**（ユーザー固有） |

`.env`にトークンを直書きできるのは、前述の「自分専用のショートカット」を使った個人用スクリプトの場合だけ。

保存方法（暗号化するか、どこに置くか）の検討は [token-storage.md](token-storage.md)。

## OAuth 1.0a（旧規格）

> **現在ではほぼ絶滅している。** Google・GitHub・Slackなどはすべて2.0のみ。Twitter (X) がOAuth 1.0aの発祥元であり、後方互換のために残しているのが主な生き残り。
> **学ぶ価値は「なぜ2.0がああいう形になったか」を理解するため。**

### なぜ署名するのか

OAuth 1.0aが設計された2007年頃、Webはまだ**HTTPが当たり前**だった。通信路が暗号化されていないので、トークンを生で送れば盗聴される。

そこでこうした。

> **秘密の値そのものは送らない。「秘密を知っている」ことだけを証明する。**

このため1.0aでは、鍵が**2組4つ**になる。

| 鍵                                     | 役割             |
| -------------------------------------- | ---------------- |
| Consumer Key / **Consumer Secret**     | アプリの名札     |
| Access Token / **Access Token Secret** | ユーザーの委任状 |

**Secretは「送るもの」ではなく「署名を計算するための鍵」。**

### 手順

リクエストを送るたびに、ライブラリが裏でこれを行う。

1. これから送るリクエスト（HTTPメソッド、URL、パラメータ、nonce、timestamp）を決まった手順で1本の文字列にまとめる（**signature base string**）
2. `Consumer Secret` + `&` + `Access Token Secret` を連結して**署名鍵**を作る
3. その鍵でbase stringを**HMAC-SHA1**にかける → **signature（署名）**
4. 送るのは以下。**Secretは含まれない**

```
Authorization: OAuth
  oauth_consumer_key="...",     ← 名乗り（アプリ）
  oauth_token="...",            ← 名乗り（ユーザー）
  oauth_signature="...",        ← 証明
  oauth_nonce="...",
  oauth_timestamp="...",
  oauth_signature_method="HMAC-SHA1"
```

### サーバー側の検証

```
クライアント側:  Secret ──┐
                          ├─→ HMAC計算 → signature ──→ 送信
             リクエスト内容 ──┘

サーバー側:      Secret ──┐                            ↓
            （DBから引く）├─→ HMAC計算 → signature  ⟷ 照合
             リクエスト内容 ──┘  （自分で作った方）
```

サーバーは`oauth_consumer_key`と`oauth_token`を見て、**自分のDBから対応するSecretを引く**（発行したのは自分なので当然知っている）。そして**まったく同じ計算をやり直し**、出てきた署名が送られてきたものと一致するかを見る。

**照合しているのはSecretではなく、signature（計算結果）。** Secretは届いていないので照合しようがない。

> 署名が一致した = 相手も同じSecretを持っていた = 本物

これは [hash-and-encryption.md](hash-and-encryption.md) のパスワード認証とまったく同じ構造。**元に戻して比較しているのではなく、もう一度同じ計算をして結果が一致するかを見ている**だけ。

### Secretが2つとも必要な理由

署名鍵が**2つのSecretの連結**であることがポイント。**片方だけでは正しい署名が作れない。**

- アプリのSecretだけ盗んでも、ユーザーのSecretがないので署名できない
- ユーザーのSecretだけ盗んでも、アプリのSecretがないので署名できない

「**このアプリが、このユーザーの許可を得て喋っている**」ことの暗号的な表現になっている。前述の「2つの問い」が、署名鍵の中で合流している。

### リプレイ攻撃への対策

署名が正しくても、**盗聴した第三者がリクエストを丸ごとコピーして再送信**すれば署名は正しいまま通ってしまう（リプレイ攻撃）。

対策として、毎回**nonce**（number used once = 使い捨てのランダム文字列）と**timestamp**を混ぜて署名する。サーバーは「そのnonceは使用済み」「そのtimestampは古すぎる」と弾ける。同じリクエストは二度と通らない。

### 2.0で何が変わったか

2012年頃にはWebのHTTPS化が進んだ。**通信路そのものが暗号化されているなら署名は要らない**、という判断で、OAuth 2.0は署名を廃止した。

| OAuth 1.0a          | OAuth 2.0                               |
| ------------------- | --------------------------------------- |
| Consumer Key        | **Client ID**（残る・名前だけ変更）     |
| Consumer Secret     | **Client Secret**（残る・名前だけ変更） |
| Access Token        | Access Token（残る）                    |
| Access Token Secret | **消滅**                                |

**Access Token Secretが消えたのは、アクセストークンの役割が変わったから。**

|                        | OAuth 1.0a                                           | OAuth 2.0                                    |
| ---------------------- | ---------------------------------------------------- | -------------------------------------------- |
| アクセストークンの役割 | **識別子**（「これは誰の委任状か」と名乗るだけの札） | **秘密そのもの**（持っていること自体が証明） |
| 証明の担い手           | Secretによる署名                                     | トークン自体（Bearer）                       |

識別子でしかなかったものが秘密そのものに格上げされたので、**証明を外部委託する相棒（Secret）が不要になった**。アクセストークンが秘密でいられるのは、**ブラウザに一度も出ず、サーバー間だけで受け渡されるから**。

一方**Client Secretが残った**のは、前述の通りClient IDが公開情報であり、それ単体ではアプリの証明にならないため。

> **OAuth 1.0aの複雑さは「通信路が信用できない」という前提から来ていた。その前提が消えたので、複雑さも消えた。**

## OpenID Connect

「Googleでログイン」のような**ソーシャルログインは、厳密にはOAuthではない。**

冒頭の通り、**OAuthは認可（何を許すか）であって認証（誰であるか）ではない**。しかしログインは「誰であるか」を確かめたい。**目的が食い違っている。**

実際、OAuthをそのまま認証に流用すると穴がある。アクセストークンは「このアプリはデータを触ってよい」としか言っておらず、**「このトークンの持ち主が誰か」を保証していない**。そのため、別のアプリ向けに発行されたトークンを横流しして成りすます余地が生まれる。

そこで**OAuth 2.0の上に認証レイヤーを乗せた規格**が作られた。

```
OAuth 2.0       = 認可（何を許すか）
OpenID Connect  = OAuth 2.0 + 認証（誰であるか）
```

**ID Token**（JWT形式で「誰か」が署名付きで記述されている）が追加されるのが最大の違い。「◯◯でログイン」の正体はこちら。

**認可の仕組みに、認証を後から足したもの。** だから名前が別になっている。
