# OAuth

## OAuthとは

あるアプリに、自分のデータへのどこまでの操作を許すかを扱う仕組み。RFC 6749 として標準化されていて、Google・GitHub・Slack・X など主要なサービスのほぼすべてが採用している。

"Auth" は Authentication（認証）ではなく Authorization（認可）。

| 用語                   | 意味                           |
| ---------------------- | ------------------------------ |
| Authentication（認証） | 「あなたは誰か」を確かめる     |
| Authorization（認可）  | 「あなたに何を許すか」を決める |

仕組みや流れは共通だが、エンドポイントのURL、scope の名前、トークンの有効期限などはサービスごとに違う。

## 解決したかった問題

OAuth 以前は、外部サービスに対象サービスのIDとパスワードを直接渡していた（パスワードアンチパターン）。

| 問題                     | 内容                                                             |
| ------------------------ | ---------------------------------------------------------------- |
| パスワードを預けてしまう | サービス側がパスワードを保存する。漏洩したら終わり               |
| 権限が全か無か           | 投稿だけ許可したくても、DM閲覧もアカウント削除もできてしまう     |
| 取り消せない             | やめるにはパスワードを変えるしかない。他のサービスも使えなくなる |

OAuth では、パスワードの代わりに、権限を限定して後から取り消せる合鍵（アクセストークン）を渡す。

## 登場人物

| 役       | 正式名称                        | 内容                               |
| -------- | ------------------------------- | ---------------------------------- |
| 持ち主   | Resource Owner                  | データの持ち主であるユーザー       |
| 借りる側 | Client                          | データを使いたいアプリ             |
| 管理者   | Authorization / Resource Server | データを持ち、許可を出すサービス側 |

| 例                             | Resource Owner | Client           | Server |
| ------------------------------ | -------------- | ---------------- | ------ |
| 予約投稿サービスがXに投稿する  | Xのユーザー    | 予約投稿サービス | X      |
| CIツールがGitHubをclone        | GitHubユーザー | CIツール         | GitHub |
| アプリがGoogleカレンダーを読む | Googleユーザー | そのアプリ       | Google |

## 鍵が2組ある理由

サービスは、アプリの登録とユーザーの許可を別々に管理する。そのため鍵も2組ある。

| 鍵                        | 表すもの                       |
| ------------------------- | ------------------------------ |
| Client ID / Client Secret | どのアプリか                   |
| Access Token              | 誰のデータを、許可を得て触るか |

- Client ID と Client Secret は、アプリをサービスに登録したときにもらう
- アクセストークンは、ユーザーが認可画面で許可したときに発行される
- 権限はアプリとユーザーの組み合わせごとに管理される。設定画面でアプリの許可を取り消すと、そのアプリのアクセストークンだけが無効になる

## アクセストークンの取得（認可フロー）

ユーザー・アプリ・サービスの3者が関わるので、3-legged OAuth と呼ばれる。

```
1. アプリが、ユーザーをサービスの認可画面へリダイレクトする（Client ID で名乗る）
     → 「このアプリに◯◯を許可しますか？」の画面が出る

2. ユーザーが「許可する」を押す
     → サービスが、認可された証（code）を付けて、ユーザーをアプリの callback URL へ送り返す

3. アプリが、code と Client Secret をサービスに送る
     → サービスがアクセストークンを発行する

4. 以降、アプリはアクセストークンで API を叩く
```

callback URL（リダイレクトURI）は、事前にサービスに登録しておく。リクエストで送る `redirect_uri` と完全一致で照合されるので、末尾のスラッシュ1文字が違ってもエラーになる。

## Bearer トークン

API を叩くときは、アクセストークンをヘッダにそのまま載せる。

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6...
```

Bearer は「持参人払い」の意味で、持っている人を本人とみなす。漏れたらそのまま使われるので、次の2つで守る。

- HTTPS で送る
- 有効期限を短くする

## Client Secret の出番

API を叩くときには使わない。使うのは、認可フローの3で code をアクセストークンと交換するときだけ。

```
     ブラウザ                アプリ              サービス
        |                     |                      |
        |  code=abc123        |                      |   ← ブラウザを経由するのはここまで
        |-------------------->|                      |
        |                     |  code + client_id    |
        |                     |     + client_secret  |
        |                     |--------------------->|   ← サーバー間の直接通信
        |                     |<---------------------|
        |                     |    access_token      |
```

code はリダイレクトでブラウザを通るので、盗まれる可能性がある（悪意ある拡張機能、履歴、ログなど）。Client Secret がなければ、code を盗んだ人が Client ID と組み合わせてアクセストークンを手に入れられてしまう。

SPA やモバイルアプリは Client Secret を安全に保管できない（解析すれば抜ける）ので、Client Secret を使わない PKCE という仕組みを使う（未学習）。

### Client ID は公開情報

認可フローの1で、Client ID は認可画面のURLに載ってユーザーのブラウザに届く。

```
https://<サービス>/oauth2/authorize
    ?client_id=XXXXXXXX          ← ブラウザのアドレスバーに表示される
    &redirect_uri=http://localhost:8000/callback/
    &scope=...
    &response_type=code
```

HTTPS が守るのは通信の途中だけなので、ブラウザに届いた Client ID は開発者ツールなどで読める。

## 有効期限と scope

| 概念          | 内容                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------- |
| 有効期限      | アクセストークンは短命（数十分〜数時間）                                                     |
| Refresh Token | 期限切れのときに新しいアクセストークンをもらうためのトークン。ユーザーの再ログインが要らない |
| scope         | 許可する権限の範囲。認可画面に「このアプリは◯◯にアクセスします」と並ぶのはこれ               |

| サービス | scope の例                                            |
| -------- | ----------------------------------------------------- |
| X        | `tweet.read` / `tweet.write` / `dm.read` / `dm.write` |
| GitHub   | `repo` / `user` / `gist`                              |
| Google   | `https://www.googleapis.com/auth/drive.readonly`      |

必要最小限の scope だけを要求するのが原則（最小権限の原則）。
