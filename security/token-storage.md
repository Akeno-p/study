# トークンの保存場所と暗号化

OAuthのアクセストークン・リフレッシュトークンのような「サーバーが元の値を使って外部APIを叩く必要がある秘密のデータ」を、どこに・どう保存するかの整理。

## 保存場所の選択肢

### サーバー側に保存（トークンはブラウザに渡らない）

| 方法                  | 特徴                                                               |
| --------------------- | ------------------------------------------------------------------ |
| 自作モデル（DB）      | トークン専用のテーブルを作る。暗号化を自由に実装できる             |
| キャッシュ（Redis等） | メモリ上なので高速。データが消えることがあるため短期の一時保管向き |

### クライアント側（ブラウザ）に保存（トークン本体がブラウザにある）

| 方法               | 特徴                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| Cookie             | 毎リクエストで自動送信される。つまりトークンが毎回ネットワークを流れる |
| ローカルストレージ | JavaScriptから自由に読めるため、XSSで盗まれるリスクがある              |

### 比較

| 方法                  | 暗号化の自由度   | ネットワークに流れるか | XSSで盗まれるか        |
| --------------------- | ---------------- | ---------------------- | ---------------------- |
| 自作モデル（DB）      | 自由にできる     | 流れない               | 盗まれない             |
| セッション（DB）      | 標準ではできない | 流れない               | 盗まれない             |
| キャッシュ（Redis等） | 実装次第         | 流れない               | 盗まれない             |
| Cookie                | できない         | **毎回流れる**         | HttpOnlyなら盗まれない |
| ローカルストレージ    | できない         | 流れない               | **盗まれうる**         |

## 暗号化が効く範囲

暗号化には鍵が必要で、鍵はDBとは別の場所（環境変数など）に保管する。どこまで守れるかは侵害の範囲で変わる。

- **DBだけが漏洩した場合**（SQLインジェクション、バックアップファイルの流出など）→ 鍵がないと復号できないので**非常に有効**
- **サーバーごと侵害された場合** → 環境変数から鍵も盗まれるため守れない

DB単体の漏洩は現実に起こりうるので、暗号化する価値は十分にある。

## 暗号化のデメリット

| デメリット                                                               | 深刻度                                       |
| ------------------------------------------------------------------------ | -------------------------------------------- |
| 実装の手間                                                               | 一度作れば終わり                             |
| 鍵の管理責任が増える（紛失 = 全ユーザー再認証、漏洩 = 暗号化が無意味に） | 本質的な課題。鍵の置き場所とセットで設計する |
| 鍵のローテーション（定期変更 → 全トークンの再暗号化）の仕組みが必要      | 手間がかかる                                 |
| 使用のたびに復号処理が入る                                               | 個人規模のアプリでは無視できる               |

重要なのは、仮に鍵が漏れても**「平文で保存していたのと同じレベルに下がる」だけ**で、暗号化したこと自体が新たな脆弱性（攻撃者に悪用されうる弱点）を生むわけではないこと。つまり暗号化を「やらない理由」にはならない。
