# TLS

## TLSとは

「暗号化」と「証明書のチェック」を実際にやっている仕組みの名前がTLS。

HTTPにTLSを被せたものがHTTPS（[http-https.md](../knowledge/web-technologies/http-https.md)）。HTTPは暗号化も証明書のチェックもしない。

### SSLとTLSの関係

SSLはTLSの古い名前。改良されて名前が変わった。「SSL証明書」という言い方は習慣で残っているだけで、指しているものはTLSの証明書と同じ。

## 用語の整理（先に押さえる）

「秘密鍵」という日本語は**2つの別物**に使われている。ここを混ぜると全部分からなくなるので、以下このドキュメントでは英語を併記する。

| このドキュメントでの呼び方 | 誰が持つか         | 何をする鍵か                         |
| -------------------------- | ------------------ | ------------------------------------ |
| **共通鍵（secret key）**   | 両者が同じ物を持つ | 暗号化も復号もできる                 |
| **公開鍵（public key）**   | 誰に配ってもいい   | 暗号化**だけ**できる                 |
| **秘密鍵（private key）**  | 持ち主だけ         | 公開鍵で暗号化されたものを復号できる |

英語では `secret key`（共有された秘密の鍵）と `private key`（自分だけの鍵）で単語が分かれているが、日本語ではどちらも「秘密鍵」と訳されてしまった。だから世の中の文章では、文脈で読み分ける必要がある。

**見分け方は「誰が持っているか」**。両者が持っているなら secret key、片方しか持っていないなら private key。

## 暗号化（共通鍵暗号）

お互いが**共通鍵（secret key）**を持っていて、それを使って暗号化し、受け取った時に復号する。第三者は共通鍵を持っていないので、暗号化された値を元に戻せない。

メリットは、通信を傍聴された時にデータが漏れないこと。

## 鍵はどうやって共有するのか（公開鍵暗号）

共通鍵（secret key）でやり取りするには、まずお互いが同じ鍵を持っていなければならない。しかし**その鍵を渡すやり取り自体が盗聴されている**ので、そのまま送れば鍵が漏れる。

これを解決するのが**公開鍵暗号**。鍵を**2個1組**にする。

|                           | 誰が持つか       | できること                                   |
| ------------------------- | ---------------- | -------------------------------------------- |
| **公開鍵（public key）**  | 誰に配ってもいい | 暗号化**だけ**できる。復号はできない         |
| **秘密鍵（private key）** | 持ち主だけ       | 公開鍵で暗号化されたものを復号できる唯一の鍵 |

ポイントは「**暗号化する鍵**」と「**復号する鍵**」が別物だということ。

### 「公開鍵暗号」と「公開鍵」は別の階層

「公開鍵暗号」は**方式（仕組み）の名前**。「公開鍵」はその方式で使う**鍵の片割れ**。公開鍵暗号という方式は、公開鍵と秘密鍵の**2本セット**で成り立つ。

| 方式           | 使う鍵                             | 別名                      |
| -------------- | ---------------------------------- | ------------------------- |
| **共通鍵暗号** | secret key を1本、両者で共有       | 対称暗号 / **秘密鍵暗号** |
| **公開鍵暗号** | public key と private key の2本1組 | **非対称暗号**            |

「非対称」＝暗号化する鍵と復号する鍵が非対称（別物）という意味。

なお共通鍵暗号の別名が「秘密鍵暗号」なので、「秘密鍵暗号の秘密鍵（secret key）」と「公開鍵暗号の秘密鍵（private key）」という紛らわしい2つが世の中に並んでいる。

### 南京錠の例え

- 公開鍵（public key） = **開いた南京錠**。誰にでも配れて、誰でもカチッと閉められる
- 秘密鍵（private key） = **その南京錠を開ける鍵**。持ち主だけが持っている

閉めた本人ですら、もう開けられない。**誰でも暗号化できるが、復号できるのは持ち主だけ**。

### 秘密鍵は配らない

**秘密鍵（private key）を配るタイミングは存在しない**。生成された瞬間からサーバーの中にあり、**一度もネットワークに流れない**。

配ってしまったら、その通信が盗聴された時点で終わり。それでは共通鍵と同じ問題に戻ってしまう。「配らなくて済むようにした」のが公開鍵暗号。

鍵ペアはサーバーが**自分で生成する**。

```
① サーバーが自分のマシン上で public key と private key をペアで生成
② private key → サーバーのディスクに保存。外に出さない
③ public key  → 証明書に埋め込んで、誰にでも配る
```

証明機関に渡すのも public key だけ。証明機関ですらサーバーの private key は知らない。

### 誰が何を持っているか

| 持ち物                     | サーバー | 自分（ブラウザ）        |
| -------------------------- | -------- | ----------------------- |
| サーバーの public key      | ○        | ○（配られる）           |
| サーバーの **private key** | ○        | **×（永遠に持たない）** |
| **共通鍵（secret key）**   | ○        | ○（鍵の共有後）         |

**持ち物が左右で食い違っているのが正常**。「両者が同じ鍵を持つ」のは共通鍵暗号のルールであって、公開鍵暗号はそのルールを捨てた方式（＝非対称）。

## 盗聴されている回線で鍵を共有する手順

| 手順 | 誰が     | 何をする                     | 使う鍵                     |
| ---- | -------- | ---------------------------- | -------------------------- |
| ①    | サーバー | **公開鍵を配る**             | （暗号化しない・平文）     |
| ②    | 自分     | 共通鍵を作り、暗号化して送る | サーバーの public key      |
| ③    | サーバー | 共通鍵を取り出す             | サーバーの **private key** |
| ④    | 両者     | 本番の通信                   | **共通鍵（secret key）**   |

**鍵を配るのはサーバー、暗号化するのは自分、復号するのはサーバー。**

- ①で public key は**平文で流れる**。見られてもいい鍵だから隠す必要がない。盗聴者が手に入れても、できるのは暗号化だけで何も読めない
- ②の暗号を解けるのはサーバーの private key だけ。だから途中で盗聴されても共通鍵は漏れない
- 共通鍵は**自分が作る**。送っても手元から消えるわけではないので、③が終わった時点で**両者が同じ共通鍵を持った状態**になる

### 受け取った暗号文はどう読むのか

サーバーからの返事を復号するのも**共通鍵（secret key）**。public key でも private key でもない。

共通鍵は対称（暗号化と復号が同じ鍵）なので、**どちらの方向でも暗号化・復号できる**。④の「やり取り」は行きも帰りも両方という意味。

```
【鍵の共有フェーズ】← 公開鍵暗号。一方通行でよい
① サーバー → 自分     : public key を配る
② 自分     → サーバー : 共通鍵を public key で暗号化して送る
③ サーバーが private key で復号 → 両者が共通鍵を持つ

【本番の通信フェーズ】← ここから先は全部 共通鍵。双方向
④ 自分     → サーバー : リクエストを共通鍵で暗号化 → サーバーが共通鍵で復号
⑤ サーバー → 自分     : HTMLを共通鍵で暗号化 → 自分が共通鍵で復号
```

### 公開鍵暗号が使われるのは②の一瞬だけ

実際にやり取りする中身（HTML、JSON、パスワード、画像）は、**一つ残らず共通鍵で暗号化されている**。public key / private key は本番のデータに一切触れない。

公開鍵暗号の役割は「データを運ぶこと」ではなく、**「共通鍵という1本の鍵を、盗聴された回線越しに安全に渡し切ること」だけ**。渡し終わったら主役から降りる。

理由は2つ。

- **速度**：公開鍵暗号は遅く、共通鍵暗号は速い
- **方向**：公開鍵暗号は「自分 → サーバー」の一方通行しか暗号化できない（自分は private key を持っていないので、サーバーは自分宛てに暗号化する手段がない）。双方向にするには共通鍵が要る

### 秘密鍵が使われるタイミング

private key の出番は**ハンドシェイク（鍵の共有）の間だけ**。ただし「人生で初回の1回」ではなく、**接続を張り直すたび**。共通鍵はその接続かぎりの使い捨てなので、繋ぎ直せばまた作り直す。

つまり private key は**毎回の入口で、毎回一瞬だけ**働く。逆に言えば**入口でしか働かない**。

## 間に入り込んでくる攻撃

暗号化されていても、**鍵があれば中身は見れてしまう**。だから攻撃者は鍵を得ようとしてくる。狙われるのは**鍵の受け渡しのタイミング**。

ただしやり口は「鍵を盗む」ではなく、**自分が鍵の共有相手になりすます**（すり替わる）。「私が銀行です」と名乗り出て、こちらと直接鍵を交わしてしまう。こうなると攻撃者は正規の鍵を持っているので、暗号化されていても中身が読める。

手順で言うと、①で public key が配られるところに割り込み、**攻撃者が自分の public key を「サーバーの public key です」と渡す**。こちらはそれを本物だと思って共通鍵を暗号化して送ってしまうので、攻撃者は自分の private key で復号できてしまう。

つまり公開鍵暗号だけでは、「**受け取った public key が、本当にそのサーバーのものか**」が分からない。

暗号化だけではこれを防げない。だから「**相手が本物か**」を確認する必要がある。

## 証明書

### 証明書とは

ファイル。中身は以下のような情報。

| 入っている情報                     | 例                       |
| ---------------------------------- | ------------------------ |
| どのドメインの証明書か             | example.com              |
| **サーバーの公開鍵（public key）** | 鍵の共有で配られる南京錠 |
| どの証明機関が発行したか           | Let's Encrypt            |
| 有効期限                           | 発行から90日など         |
| 証明機関の署名                     | 改ざん検知用             |

署名が入っているので、中身を書き換えても見破られる。

ここで**鍵の共有と証明書が繋がる**。手順①で配られる public key は、この証明書に入っているもの。証明書が「**この public key は確かにこのドメインのサーバーのものだ**」と証明機関の保証つきで示すので、攻撃者が自分の public key にすり替えられなくなる。

### 「偽物のサイトも証明書を取れるのでは？」

証明書は誰でも取れる。ただし取れるのは**自分が持っているドメインの分だけ**。

証明機関は発行前に「本当にそのドメインの持ち主か」を確認する。他人のドメインのサーバーは操作できないので、その確認が通らない。

| 誰が                                   | 何の証明書を   | 結果         |
| -------------------------------------- | -------------- | ------------ |
| 自分（自分のドメイン所有）             | 自分のドメイン | 取れる       |
| 攻撃者（銀行のドメインは持っていない） | 銀行のドメイン | **取れない** |

だから「誰でも取れる」けれど「**なりすましには使えない**」。

### 1ドメインにつき1枚か

複数取れる。ただし実際にサーバーに設置して使うのは1つ。

Let's Encryptの証明書は有効期限が90日なので、期限が切れる前に取り直す運用になる。

## ブラウザが実際に見ているもの

1. **正しいURLか** … 証明書に書かれたドメインと、今アクセスしているURLが一致するか
2. **ちゃんとしたところが発行した証明書があるか** … 信頼できる証明機関が発行したものか

ブラウザは最初から「信頼できる証明機関のリスト」を持っていて、それと照合している。

（おまけ）有効期限が切れていないかも見ている。

## このチェックはHTTPSだけ

HTTPには証明書という概念自体が無いので、暗号化も本物確認もしない。

|                       | HTTP       | HTTPS              |
| --------------------- | ---------- | ------------------ |
| 暗号化                | なし       | あり               |
| 証明書                | 存在しない | サーバーが提示する |
| 正しいURLかのチェック | しない     | する               |
| 発行元のチェック      | しない     | する               |

## localhostではhttpを使う

localhostには証明書が無いので、`https://localhost` にすると証明書エラーになる。ローカルでのテストでは `http://localhost` を使う。

証明機関はlocalhostの証明書を発行できない（全員のPCがlocalhostなので、誰のものか保証しようがない）。

本番はドメインを取り、Let's Encryptで証明書を発行してhttpsを使う。

## 実際のTLS 1.3との違い（ここまでは簡略モデル）

上の手順は**理解の骨格としては正しい**が、現代のTLS 1.3は少し違う。

| 項目               | ここまでの説明   | 実際のTLS 1.3                                    |
| ------------------ | ---------------- | ------------------------------------------------ |
| 共通鍵の作り方     | 自分が作って送る | **両者が材料を出し合ってその場で導く**（鍵交換） |
| private key の仕事 | 共通鍵を復号する | **署名して「本人だ」と示す**                     |

鍵交換では**共通鍵そのものが回線を流れない**ので、盗聴しても材料しか手に入らない。

そこで private key は、「**この材料を出したのは確かに example.com のサーバーだ**」と署名する役目を負う。署名は private key でしか作れず、証明書の中の public key で検証できる。

つまり private key は、**通信の中身を読むための鍵ではなく、「自分が本物だ」と名乗るための鍵**。

- private key が漏れる ＝ **誰でもそのサーバーになりすませる**
- だから絶対にサーバーの外に出さない

証明書・署名・private key は、すべて**なりすましを防ぐ**という一つの目的のための道具立て。暗号化そのものを担っているのは、あくまで共通鍵（secret key）。

### 暗号化と署名は同じ仕組みの表と裏

公開鍵暗号は逆向きにも使える。

| 向き                                     | 何になるか                     |
| ---------------------------------------- | ------------------------------ |
| public key で暗号化 → private key で復号 | **秘密が守れる**（＝鍵の共有） |
| private key で暗号化 → public key で復号 | **署名**（本人しか作れない）   |

証明書に入っている「証明機関の署名」も、この同じ公開鍵暗号を使っている。
