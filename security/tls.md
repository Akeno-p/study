# TLS

## TLSとは

通信の暗号化と、通信相手が本物かの確認をする仕組み。HTTPS はこれを使っている。

SSL は TLS の古い名前。「SSL証明書」という言い方は習慣で残っているだけで、TLS の証明書と同じもの。

## 共通鍵で暗号化する

ブラウザとサーバーが同じ共通鍵を持ち、それで暗号化・復号する。第三者は共通鍵を持っていないので、盗聴しても中身を読めない。

共通鍵は接続ごとに作る使い捨て。

共通鍵は英語で secret key。公開鍵暗号の秘密鍵（private key）とは別物だが、日本語ではどちらも「秘密鍵」と呼ばれることがある。両者が同じものを持つなら共通鍵、片方だけが持つなら秘密鍵。

## 共通鍵の決め方（鍵交換）

共通鍵をそのまま送ると、盗聴されて漏れる。そこで、ブラウザとサーバーがそれぞれ材料を出し合い、両者がその場で同じ共通鍵を計算して導く。

- 回線に流れるのは材料だけで、共通鍵そのものは流れない
- 材料を盗聴しても、共通鍵は計算できない

## なりすましの防ぎ方

鍵交換だけでは、相手が本物か分からない。攻撃者がサーバーになりすまして材料を出せば、ブラウザは攻撃者と共通鍵を作ってしまい、中身を読まれる。

そこでサーバーは、証明書と署名を送る。

| 送るもの | 示すこと                                                               |
| -------- | ---------------------------------------------------------------------- |
| 証明書   | この公開鍵は、このドメインのものだ                                     |
| 署名     | 自分はその公開鍵とペアの秘密鍵を持っている。鍵交換の材料を出したのも自分だ |

署名の対象は、ブラウザが出したお題と鍵交換の材料を含むやり取り。ブラウザは証明書の公開鍵で署名を確かめる。

サーバーの秘密鍵は、通信の中身を読むための鍵ではなく、本物だと示すための鍵。漏れると誰でもそのサーバーになりすませるので、サーバーの外に出さない。

### 証明書だけでは足りない理由

証明書は接続してきた全員に配る公開情報なので、誰でもコピーできる。

```
1. 攻撃者が、本物の youtube.com の証明書をコピーする
2. 偽のDNSサーバーや偽のWi-Fiで、ユーザーを攻撃者のサーバーに誘導する
3. 攻撃者のサーバーが、コピーした証明書を送る
```

証明書の中身はすべて本物なのでチェックは通るが、攻撃者は秘密鍵を持っていないので、確かめて通る署名は作れない。

## 接続の流れ

youtube.com にアクセスする場合。通信を始めるのはブラウザ側。

```
1. DNS
   ブラウザ → フルリゾルバー : youtube.com のIPアドレスを教えて        （暗号化なし）

2. TCP接続
   ブラウザ → サーバー : 「これから通信するよ」                        （暗号化なし）
   サーバー → ブラウザ : 「いいよ」                                    （暗号化なし）

3. TLSハンドシェイク
   ブラウザ → サーバー : 「youtube.com に用がある」、お題、鍵交換の材料（暗号化なし）
   サーバー → ブラウザ : 鍵交換の材料                                  （暗号化なし）
   ── ここで共通鍵が決まる ──
   サーバー → ブラウザ : 証明書、署名                                  （暗号化あり）
   ブラウザ            : 証明書をチェックして、署名を確かめる

4. 本番の通信
   ブラウザ ⇄ サーバー : ページの中身など                              （暗号化あり）
```
