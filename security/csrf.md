# CSRF について

## CSRF（クロスサイト・リクエスト・フォージェリ）とは

ログイン中のユーザーに、悪意ある外部Webサイト（罠サイト）を踏ませることで、**「本人が意図していないリクエスト（送金、ツイート、パスワード変更など）」を勝手に送信・実行させる攻撃**。

## 攻撃が成立する仕組み

ブラウザが持つ「対象ドメイン宛のリクエストには、保存されているCookie（セッション情報）を自動で添付して送信する」という仕組みが悪用される。

1. ユーザーが正規サイト（例: `bank.com`）にログインする（ブラウザにセッションCookieが保存される）
2. 同じブラウザの別タブで、攻撃者の罠サイト（例: `evil.com`）を開いてしまう
3. 罠サイトの裏側で、`bank.com/送金リクエスト` 宛のPOST通信が勝手に実行される
4. ブラウザが自動的にユーザーのログインCookieを添えて送信する
5. サーバー側はCookieが付いているため「本人の正規リクエスト」と誤認して処理を実行してしまう

## 対策：CSRFトークン

サーバーが発行するランダムな秘密の合言葉（CSRFトークン）を使い、**「正規の画面から送られたリクエストか？」** を検証する。

### トークンの仕組み
1. **画面描画時**: サーバーが生成したトークンを **HTML（`<input type="hidden">` やメタタグ）に埋め込んで** 返す。
2. **送信時**: ブラウザから送信する際、フォームデータやリクエストヘッダーにトークンを含めて送る。
3. **検証時**: サーバー側で保持しているトークンとリクエストのトークンが一致するか照合する。

### なぜCSRFトークンで防げるのか

ブラウザの **同一生成元ポリシー（SOP: Same-Origin Policy）** により、外部の罠サイト（`evil.com`）のJavaScriptは、正規サイト（`bank.com`）の画面内の情報（HTMLやJS変数）を読み取ることができない。

- 罠サイトはCookieを自動送信させることはできても、画面内の **「CSRFトークン」の値を知ることはできない**
- サーバー側で「Cookieだけでなく、正しいCSRFトークンも送られてこないと拒否する」とルール化することで、罠サイトからの偽リクエストを弾くことができる

### コードレビューでのチェックポイント
- **データの更新・削除をGETメソッドで行っていないか？**
  - GETは通常CSRF検証の対象外。状態変更（作成・更新・削除）は必ず POST / PUT / DELETE にする。
- **サーバー側のCSRF検証を意図せず無効化（スキップ）していないか？**
  - フレームワークの検証スキップ設定（`skip_before_action` や除外リスト等）が安易に使われていないか確認する。
- **非同期通信（Ajax / Fetch）でもトークンを送っているか？**
  - 通常のHTMLフォームだけでなく、JS通信時にリクエストヘッダー（`X-CSRF-TOKEN` 等）へトークンを付与しているか確認する。

#### 補足・セキュリティ上の注意点
- **JS変数にトークンを保持してよいか？**: 問題ない。本人が見る分には害がなく、外部の罠サイトからはSOPによって読み取れないため。
- **外部ドメインへのリクエスト**: 外部API等へAjaxを投げる際は、誤って自社のCSRFトークンを漏洩させないよう、内部通信であるか（`!this.crossDomain`）のチェックを入れるのがより堅牢。
- **XSSとの関係**: アプリにXSS脆弱性がある場合、同一画面内でスクリプトが動くため、CSRFトークンごと読み取られて突破される（CSRF対策だけではXSSは防げない）。
