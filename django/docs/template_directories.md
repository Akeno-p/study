# テンプレートの置き場所について

`{% extends %}` や `render()` で指定する「テンプレート名」が、実際にどのファイルへ解決されるのかという話。
テンプレートの**構文**については `templates.md` を参照。

---

## テンプレートの探索経路は2つある

Djangoはテンプレートを探すとき、**2種類の経路**を持っている。両者は競合しておらず、役割が違う。

### 💡 概要

| 設定           | 探す場所                        | 役割                                             |
| -------------- | ------------------------------- | ------------------------------------------------ |
| **`DIRS`**     | プロジェクト直下の `templates/` | 自分が書くテンプレート ＋ サードパーティの上書き |
| **`APP_DIRS`** | 各アプリの `<app>/templates/`   | サードパーティが持ち込むテンプレートのデフォルト |

- `APP_DIRS: True` は「`INSTALLED_APPS` に登録された全アプリの `templates/` を探せ」という意味。
- ディレクトリ名は **`templates` でなければならない**。Djangoのソースにハードコードされており、設定で変更できない（`static` と同じ）。
- `INSTALLED_APPS` に登録されていないアプリの `templates/` は**完全に無視される**。

### ✒️ 設定

```python
# settings.py
TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [BASE_DIR / "templates"],   # プロジェクト共通の置き場
        "APP_DIRS": True,                   # 各アプリの templates/ も探す
        ...
    },
]
```

### ⚠️ `APP_DIRS: True` は絶対に切ってはいけない

「アプリ内にテンプレートを置かないなら `False` でいいのでは」と思うが、**`django.contrib.admin` も `django.contrib.auth` もテンプレートをアプリ内に持っている**。切ると管理画面が丸ごと壊れる。

## 探索順序（先に見つかったほうが勝つ）

### 💡 概要

- Djangoは探索ルートを**上から順に**見ていき、**最初に見つかったファイルを使う**。
- 順序は `DIRS` → `APP_DIRS`（`INSTALLED_APPS` の登録順）。
- **自作アプリは `INSTALLED_APPS` の末尾に書かれるため、探索順は最後になりがち**。

### ✒️ 実際の探索順

```
1. ./templates                                     ← DIRS（最優先）
2. .../django/contrib/admin/templates              ← APP_DIRS
3. .../django/contrib/auth/templates               ← APP_DIRS
4. ./users/templates                               ← APP_DIRS（自作アプリは最後）
```

自分のアプリが**負ける側**にいることを理解しておく。

## 名前空間（なぜ `users/templates/users/` と2段掘るのか）

### 💡 概要

- **Djangoのテンプレート名前空間はフラット**。全アプリの `templates/` が1つの空間にマージされる。
- そのため `users/templates/login.html` は、Djangoにとってただの **`login.html`** になる。「どのアプリのものか」という情報は消える。
- 別のアプリも `login.html` を持っていた場合、**探索順が早いほうが勝ち、負けたほうは黙って無視される**。
- **エラーにならない**。画面は普通に表示される。ただし自分が書いたものではない。これが一番怖い。

```
users/templates/login.html   → テンプレート名は "login.html"        （衝突する）
users/templates/users/login.html → テンプレート名は "users/login.html" （衝突しない）
```

### 💡 Django自身も全アプリで名前空間を切っている

```
django/contrib/admin/templates/
├── admin/          ← 名前空間
└── registration/   ← 名前空間

django/contrib/auth/templates/
├── auth/           ← 名前空間
└── registration/   ← 名前空間

→ 直下に .html を置いているアプリは ゼロ
```

### 💡 なぜ自動で名前空間を付ける設計にしなかったのか

技術的には可能だったが、そうすると**サードパーティのテンプレートを外から上書きできなくなる**。

> **「自動名前空間の安全さ」と「オーバーライドの自由」はトレードオフ。Djangoは後者を取った。**
> **その代償が、開発者に手で `users/` を掘らせること。**

`users/templates/users/` が冗長に見えるのは**気のせいではない**。実際に冗長であり、Djangoの設計上の妥協点。

## 2つの流派（集約方式 と アプリ内方式）

テンプレートの置き場所には2つの流派があり、**どちらも正当**。

### 💡 比較

|                    | **集約方式**                 | **アプリ内方式**                   |
| ------------------ | ---------------------------- | ---------------------------------- |
| パス               | `templates/users/login.html` | `users/templates/users/login.html` |
| テンプレート名     | `users/login.html`           | `users/login.html`（同じ）         |
| アプリ名の出現回数 | **1回**                      | **2回**（冗長）                    |
| 拾われる設定       | `DIRS`                       | `APP_DIRS`                         |
| 探索順             | **1番目（絶対に勝つ）**      | 最後（負ける可能性あり）           |
| 見通し             | 全テンプレートが1箇所        | アプリごとに分散                   |
| アプリの再利用     | ❌ できない                  | ⭕️ 他プロジェクトに持ち出せる      |

### 💡 どちらを選ぶか

**判断基準は1つだけ。「そのアプリを他プロジェクトに持ち出す予定があるか」。**

- **ある**（`pip install` できるアプリを作る等） → **アプリ内方式**。そうするしかない
- **ない**（自分のためのシステムを一から作る） → **集約方式**でよい

自分でシステムを作る場合、冗長さがなく、衝突にも構造的に強い**集約方式のほうが素直**。

ただし `APP_DIRS: True` は残すこと（サードパーティのために必要）。**両方の仕組みが並行して動く**。
